Application platform

Datasheet and development guide for applications of the perINKpheral desk display: what the platform gives an application, what it holds it to, and how to write one that belongs on an e-paper panel.

Part I is the datasheet: the numbers and the model. Part II is the guide: how to build an application, with recommendations. Part III is the reference: every call of the host API (ABI 2) and of the SDK library.

Part I. Datasheet

1. Overview

perINKpheral is a desk companion: a 4.2" black-and-white e-paper panel and four buttons on an ESP32-C6. It shows what one glances at - the time, the weather, the next meeting, the state of a home - and stays silent otherwise. The firmware (the host) does not change with what the device shows: everything the user sees beyond the menu and the settings is an application, installed from a catalog without reflashing.

An application is a WebAssembly module and a manifest. It is written in C against one header, sdk/host_api.h, and run by an interpreter (wasm3) inside the host. The host's own pages - Settings, Device, About - are applications written with the same header.

Features

  • 400 x 300 pixels, 1 bit, with dithered greys; partial refresh in about half a second
  • Four buttons with short and long presses, and their down and up edges
  • Sandboxed: one 64 KB page of memory, no pointers into the host, no sockets
  • HTTP and HTTPS requests made by the host: scheduled polls and requests of the application's own, to the servers its manifest names
  • JSON answers picked apart by the host; any answer streamed in 1 KB pieces
  • Runs without being on the screen: answers, alarms and device events load the application for one call
  • A key-value store and files of its own that outlive it
  • The host's design system: lists, notices, pickers, cells, the row of buttons
  • Notifications shown by the host over whatever is on the screen
  • Settings declared in the manifest and edited on the device's web page
  • Strings in the user's language, loaded by the host; text in Latin with marks, Cyrillic and Greek
  • Tools that build, check and measure an application, and drive a device over the network

The model in one paragraph

There is no main() and no loop. An application exports handlers with fixed names and the host calls them: a button was pressed, a timer ran out, data arrived, the picture is wanted. A handler changes the application's state and asks for a redraw; the host calls app_on_draw() when it needs the frame, and decides itself whether and how the panel is refreshed. One application is in memory at a time. It is unloaded when it leaves the screen, so whatever must be remembered lives in its store, not in its variables.

3. Execution model

An application is not a process. It exists in memory only while the host has a reason to call it, and every such reason is one of its exported handlers.

When an instance exists

What happenedThe instanceHandlers, in order
The user opened the applicationloaded, stays while it has the screenapp_init, app_on_focus, app_on_draw ... app_on_blur, app_on_terminate
An answer, an alarm, an intent or a change of settings, while it is on the screenthe same instanceapp_on_data / app_on_values / app_on_alarm / app_on_intent / app_on_settings
The same, while it is not on the screenloaded for the call, unloaded after it; what was on the screen is set aside and returnsapp_init, the handler, app_on_terminate
It asked for the screen (request_focus()) and the host agreedstays, on top of what was there... app_on_focus, app_on_draw
It left the screen: BACK, the menu, another application on topunloadedapp_on_blur, app_on_terminate

What a handler may count on

  • One handler runs at a time, to its end. Nothing of the host or of another application runs meanwhile, so there is nothing to lock.
  • It has 3 seconds. A handler still running then is stopped; so is one that traps (a wild pointer, a call the host does not have). The application is ended and the screen says so; the host carries on.
  • It returns nothing. What it wants - a redraw, the screen, to leave - it requests, and the request takes effect when it returns.
  • app_init() has run before any other handler of the instance.
  • Presses are not lost and arrive in order. Timers of one number collapse into one. The pieces of one answer arrive in order with nothing between them.
  • An answer taken off the screen may simply stop: the user pressed a button and the instance was unloaded. app_on_terminate() is then the end of it; the poll is asked again in a minute.

State

Globals do not survive an unload, and an unload follows every visit to the screen and every call in the background. Read the state in app_init(), write it in app_on_terminate() - the last call an instance gets, whatever the reason - or at the moment it changes if it must not be lost to a loss of power.

Do not store a moment as "ticks since the start" and expect it to mean anything later: store time_now(), or time_uptime_ms() together with time_boot_id(), which is another number after every restart.

Who owns the screen

Moving about is a stack. The menu is at the bottom. Opening an application puts it on top; a notification, a question of the host's, an application that asked for the screen go on top of that. BACK is one step down; a long press of BACK empties the stack. Only the top is loaded, so an application that waits under another enters again from what it stored.

Between the surface and the panel stands the host. It compares the frame an application drew with what the panel shows, sends only what differs, and refuses a refresh that comes too soon after the last one that nobody asked for. An application cannot refresh the panel, and cannot leave a half-drawn screen.

Part II. Development guide

4. A first application

What is needed

  • wasi-sdk 34 or newer, for clang with the wasm32 target; WASI_SDK_PATH points at it.
  • Python 3, standard library only, for the tools.
  • A checkout of the perinkpheral repository: sdk/ and tools/.
  • A device on the same network, with a firmware built with the development tools (the default). Its address is on its Device page; export it once as PERINKPHERAL_HOST.

Create, build, run

tools/devtool/devtool.py new my-app --title "My app"     # a folder with the SDK's sample in it
tools/devtool/devtool.py run my-app                      # build, upload, restart the device into it
tools/devtool/devtool.py serve my-app                    # a page with the live screen, buttons, log, Run

run takes about ten seconds and does not reflash anything. serve is for working beside an editor: the screen as the panel shows it, the four buttons (and the keyboard's arrows, Enter and Backspace), the device's log as it is written, and a button that builds and uploads again.

In an IDE that reads CMake - CLion, VS Code - open the application's folder: new wrote a CMakeLists.txt into it. The code is understood with the SDK's headers and the generated strings.h and pictures.h, and my-app, my-app-run and my-app-serve are build targets. The IDE needs WASI_SDK_PATH and PERINKPHERAL_HOST in the environment it gives CMake.

The sample, whole

#include "app_text.h"
#include "host_api.h"

#define MARGIN 16

static const char PRESSES_KEY[] = "presses";
#define PRESSES_KEY_LENGTH ((int32_t)sizeof PRESSES_KEY - 1)

static int32_t presses;

static void draw_line(int32_t line, const char *text)
{
    int32_t line_height = gfx_font_height(HOST_FONT_TEXT);
    gfx_text(MARGIN, MARGIN + line * line_height, HOST_FONT_TEXT, text, app_text_length(text));
}

void app_init(void)                 /* the state comes from the store */
{
    kv_get(PRESSES_KEY, PRESSES_KEY_LENGTH, &presses, sizeof presses);
}

void app_on_terminate(void)         /* and goes back before the instance is unloaded */
{
    kv_set(PRESSES_KEY, PRESSES_KEY_LENGTH, &presses, sizeof presses);
}

void app_on_button(int32_t event)   /* a handler changes the state and asks for a redraw */
{
    switch (event) {
    case BTN_UP_PRESSED:
    case BTN_OK_PRESSED:
    case BTN_DOWN_PRESSED:
        presses++;
        request_redraw(HOST_REDRAW_NORMAL);
        break;
    }
}

void app_on_draw(void)              /* and this paints the state, all of it, on a white surface */
{
    char       counter_buffer[32];
    app_text_t counter;
    app_text_start(&counter, counter_buffer, sizeof counter_buffer);
    app_text_add(&counter, "Presses: ");
    app_text_add_number(&counter, presses);

    draw_line(0, "Hello from wasm");
    draw_line(2, counter_buffer);
}

BACK is not handled: a short press of BACK leaves an application that does not take it.

Settings

A setting is declared, not coded: the device's page draws the form from the manifest without running the application, and stores each value as text under its key in the application's own store. The code reads it with kv_get(). A change arrives as app_on_settings(), and the host fetches the polls again at once.

  • A url or link is the user's to write and the application's only to read: kv_set() on it is refused. When it changes, the secrets that were not given again with it are forgotten - a token is never sent to an address it was not meant for.
  • title is 1 - 31 characters, help up to 95.

6. The screen

Surface and colour

  • The origin is the top left of the surface. gfx_width() and gfx_height() give its size; lay out against them, not against 400 and 260.
  • Drawing works only inside app_on_draw(), on a surface that arrives white. Anywhere else a gfx_* or ui_* call returns HOST_ERR_NOT_DRAWING. What is drawn outside the surface is clipped.
  • gfx_color() sets how dark the next calls draw, from HOST_PAPER (0) to HOST_INK (16). Every app_on_draw() starts in ink. Levels between are a dither: for areas and bars. A thin line or small text in grey falls apart.
  • The host's margin is HOST_UI_MARGIN, 16 px. Keep it.

Fonts

A font is a size. The typeface is the user's choice - Departure Mono, monospaced, or Jersey, whose letters have their own widths - so a layout made by counting characters is wrong for half the users. Measure: gfx_text_width(), gfx_font_height(), gfx_font_ascent(), gfx_font_cap_height().

  • The y of gfx_text() is the top of the line, not the baseline. To put the top of the capitals at top, draw at top - (ascent - cap_height).
  • Add HOST_FONT_TABULAR to the font for digits that change in place - a clock, a countdown: every digit then takes the room of the widest. Measure with the same flag.
  • gfx_text_fit() cuts a text to a width with "..." after it, between characters. Never cut text by bytes.

Letters beyond ASCII

Text is UTF-8 and is passed on as it came. The host draws each character by the first of these that applies:

  1. its own glyph - printable ASCII always; Latin letters with marks, Cyrillic and Greek when the user has added the pack (Settings, Language, on the device's page);
  2. its spelling in ASCII - "Moskva", "Strasse", "Athina", a typographer's dashes and quotes as plain ones;
  3. a ?.

The degree sign is drawn in every size, pack or no pack. Widths differ between the three cases, which is one more reason to measure. Limits on text a person reads - a title, an option - are counted in characters, and a field holds half as many letters of two bytes as of one.

Pictures and icons

The host has twenty icons, 11 cells square: signal, no signal, four arrows, check, cross, plus, minus, trash, gear, clock, hourglass, bell, info, warning, play, pause, update. gfx_icon() draws one with a cell of any number of pixels; ui_icon() at the host's three sizes, 22, 44 and 99 px.

An application's own drawings go into pictures/ - a PNG, a PBM, or a text file of rows of # and ., which may hold several under names:

// pictures/things.txt                     #include "pictures.h"   /* made by mkapp */

A picture is a bit a cell, an eighth of what its rows would take as text, and is drawn with a cell of 1 to 16 pixels, so one drawing serves several sizes. Draw on the grid the host's icons use - 11 cells, or 22 and 44 for finer work - and the application's pictures stand beside the host's without looking foreign. A picture too large for the module goes into files/ and is drawn from there with gfx_bitmap_file(), without passing through the application's memory.

There is no budget on redraws: the device is its owner's. Every refresh nevertheless costs battery and a little of the panel's life, and a panel that keeps changing stops being something one can ignore. Section 13 says what follows.

7. Buttons

The buttons mean the same everywhere in the host: UP, OK, DOWN, BACK. Keep the meaning.

A press arrives twice over: as it happens - KEYDOWN, then KEYUP - and as what it meant - PRESSED after the key went up, or LONG_PRESSED while it is still held, the release then being only a KEYUP. Most applications handle the last two and ignore the rest. One number carries the button and the action, and has a name:

void app_on_button(int32_t event)
{
    switch (event) {
    case BTN_OK_PRESSED:       start();  break;
    case BTN_OK_LONG_PRESSED:  reset();  break;
    }
    request_redraw(HOST_REDRAW_NORMAL);
}

BACK

The applicationA short press of BACK
does not export app_on_back()leaves it: one step down the stack. Nothing to write
exports app_on_back()is delivered there. Go a page back; from the first page call request_exit()

BTN_BACK_PRESSED never reaches app_on_button(), and a long press of BACK is always the host's menu. request_exit() is one step down - the user returns to what they were looking at, which matters for an application that took the screen by itself.

Lists, pickers, dates

#include "app_ui.h"

static app_list_t list = { .count = 12 };          /* .selected = -1: facts, nothing to choose */

void app_on_button(int32_t event)
{
    switch (app_list_button(&list, event)) {
    case APP_UI_DONE:      open_item(list.selected);               break;   /* OK */
    case APP_UI_CHANGED:   request_redraw(HOST_REDRAW_NO_BLINK);   break;   /* UP, DOWN */
    default:               break;
    }
}

void app_on_draw(void)
{
    int32_t first = app_list_first(&list);
    for (int32_t row = first; row < first + ui_list_visible(&list) && row < list.count; row++) {
        ui_list_row(&list, row, label_of(row), label_length(row), "", 0, HOST_ICON_NONE);
    }
}

app_picker_t and app_date_t work the same way: a struct the application keeps, one call for a button that answers changed, done or cancelled, one call to draw.

8. Storage

The store

kv_get() and kv_set() keep small values under short keys, in a namespace no other application can reach. It holds the application's state and its settings, and it outlives the application: one that is removed and installed again finds what it left.

typedef struct { int32_t version; int32_t minutes; int64_t ends_at; } state_t;
static state_t state;

void app_init(void)
{
    if (kv_get("state", 5, &state, sizeof state) != sizeof state || state.version != 2) {
        state = (state_t){ .version = 2, .minutes = 25 };     /* nothing stored, or an older layout */
    }
}
  • Give a stored struct a version and check it: the next version of the application reads what this one wrote.
  • Every write wears the flash. Write when something changed that is worth keeping, not on every tick.
  • kv_set() with a length of 0 removes the key.

Files

For what does not fit a value: a list fetched from the network, a cache, a picture. file_read() and file_write() take an offset, so a file is read and grown in parts without ever being whole in memory. The files of the package's files/ folder are there from the install.

9. The network

An application never connects to anything. It says what it wants; the host makes the request, one at a time for the whole device, and hands over the answer - whether the application is on the screen then or not. There is no "is the network there": ask, and "no network" is one of the answers.

WayWhenThe answer arrives as
a poll with pickon a schedule, with no code runningapp_on_values(): the values of the paths, once
a poll withouton a scheduleapp_on_data() in pieces, under the poll's number
http_request()when the code decides: after a press, as a second stepapp_on_data() in pieces, under the tag the application chose (16 - 255)

Values picked by the host

#include "app_values.h"
enum { VALUE_TEMPERATURE, VALUE_CODE };            /* the order of "pick" in the manifest */

void app_on_values(int32_t request, int32_t http_status)
{
    int32_t tenths, code;
    last_status = http_status;                     /* for ui_reason(), when there is nothing to show */
    if (http_status == 200 &&
        app_value_number(VALUE_TEMPERATURE, 1, &tenths) &&      /* "21.46" becomes 215 */
        app_value_number(VALUE_CODE, 0, &code)) {
        keep(tenths, code);                        /* into the store */
    }                                              /* else: what was shown before stays */
    request_redraw(HOST_REDRAW_NORMAL);
}

There is no floating point: a number is read with as many decimals as asked for, rounded, as an integer. A path the answer did not have is missing - treat it as no data, not as zero.

An answer in pieces

void app_on_data(int32_t request, const uint8_t *data, int32_t length, int32_t flags, int32_t http_status)
{
    if (flags & HOST_DATA_FAILED) {                /* alone, with no data: http_status is a HOST_FAILED_* */
        last_status = http_status;
        return;
    }
    if (flags & HOST_DATA_FIRST) {                 /* the HTTP status comes with the first piece */
        last_status = http_status;
        begin_reading();                           /* always start afresh here */
    }
    read_piece(data, length);                      /* valid only until the handler returns */
    if (flags & HOST_DATA_LAST) {
        take_what_was_read();                      /* only now is the answer whole */
        request_redraw(HOST_REDRAW_NORMAL);
    }
}
  • Read as the pieces come - a state machine, the SDK's json_pick, a parser of the application's own - and keep only what will be shown. The answer may be megabytes; the application has 64 KB.
  • Replace what is shown only at HOST_DATA_LAST. An answer may stop half-way with no last piece and no failure (section 3); HOST_DATA_FIRST is always a fresh start.
  • data_response() gives, inside the handler, what is known of the answer beside its data: the status, Content-Length and -Type, ETag, Last-Modified, Location, Link, Retry-After.

A request of the application's own

enum { REQUEST_TOGGLE = HOST_REQUEST_FIRST };
static const char URL[]     = "{{server}}/api/services/light/toggle";
static const char HEADERS[] = "Authorization: Bearer {{token}}\nContent-Type: application/json";

http_request(REQUEST_TOGGLE, HOST_HTTP_POST, URL, sizeof URL - 1, HEADERS, sizeof HEADERS - 1,
             body, body_length);
  • Only to the manifest's hosts. {{key}} works in the URL and in header values, so the code never holds the token.
  • HOST_ERR_NO_SPACE: both waiting places of the device are taken. Ask again later.
  • A GET is followed through up to three redirects, and never out of the hosts: that fails with HOST_FAILED_NOT_ALLOWED. A request with a body is not sent twice: its redirect is the answer.
  • poll_now(n) fetches a poll now - the user pressed "refresh". poll_set_interval(n, seconds) changes its pace from the code, when a setting in the manifest is not enough: a server's Retry-After, say.

When there is no answer

StatusWhat happened
HOST_FAILED_NO_NETWORK (-1)the device is not on a network
HOST_FAILED_NO_ANSWER (-2)the server did not answer, or not to the end
HOST_FAILED_NOT_READY (-3)a {{setting}} the request needs is not set
HOST_FAILED_NOT_ALLOWED (-4)redirected to a host the manifest does not list

Keep the last status in the store and hand it to ui_reason() when there is nothing to show: it draws the host's notice for every one of these and for the HTTP statuses a user can do something about, and returns 0 for an answer that came, leaving the application to say what is missing then.

11. Time

  • time_now() is unix seconds, and 0 until the device first learns the time. Draw something sensible for that case.
  • Everything a person reads is local time, and the zone is the host's: time_local() takes the present apart, time_local_at() any moment, time_from_local() puts one together ("07:30 tomorrow" for alarm_set_at()).
  • time_text() writes a moment in words, in the device's language, so that no application carries the names of days and months: "15:04", "Fri 13 Nov", "Friday", "13 November", and - as near as it is - "15:04", "Tmrw 15:04", "Sat 15:04", "21 Nov".
  • To be told when the clock is set, ask for the time_changed intent.

12. Languages

What an application says, it says in the language the device is set to. The translations are the developer's - nobody else knows what the words are for - and the host puts them in place.

strings/en.json    { "no_events": "No events", "starts_in": "In {0} min" }
strings/ru.json    { "no_events": "Нет событий", "starts_in": "Через {0} мин",
                     "manifest": { "title": "Календарь",
                                   "settings": { "every": { "title": "Обновление",
                                                            "options": { "15 min": "15 мин" } } } } }
#include "strings.h"                              /* made by mkapp: STR_NO_EVENTS, STR_STARTS_IN, app_string() */

const char *text = app_string(STR_NO_EVENTS);     /* the text in the device's language: no call, no copy */

const host_text_argument_t minutes = { .number = 10 };
char line[32];
int32_t length = text_fill(app_string(STR_STARTS_IN), app_text_length(app_string(STR_STARTS_IN)),
                           &minutes, 1, line, sizeof line);          /* "In 10 min" */
  • en.json is required and is built into the module: an application always speaks English. Every other file must have exactly the same keys.
  • When an instance is loaded the host copies the table of the device's language over the English one in the application's memory. Reading a string then costs no code.
  • {0}, {1} in a string are filled by text_fill() with numbers or texts, in whatever order the language puts them. There are no plural forms: write so that none is needed ("min", not "minutes").
  • The key manifest in a translation carries what of the manifest a person reads: the title, a setting's title and help, labels for a choice's options. The option itself - what is stored and what the code compares - does not change.
  • The build fails on a language the system does not know (sdk/languages.json: 27 of them, by two-letter codes), on a translation with a missing or an extra key, and on a letter the language's glyph packs do not have.
  • A translation is longer than the English, as a rule by a third. The kit cuts what does not fit with "..."; whether it still reads is the translator's to check on the screen.

13. Design rules

The platform enforces little. These are the rules an application is expected to hold itself to; the host's own screens follow them.

It is paper, not a display

One thing a screen. A user looks at the device for a second from a metre away. Decide what the one value is, make it the largest thing on the screen, and let everything else be small beside it.
Nothing moves. No animation, no blinking, no progress bar that advances by itself. A bar shows a quantity and changes when the quantity does. Work going on is said, not shown: a notice with is_working.
Change when the data does. Redraw from a timer only when the picture would differ - a clock once a minute, at the turn of the minute, not once a second. A refresh nobody asked for is limited to one a minute by default; design for that pace, not against it.
Black on white. Ink on paper, a grey only for areas. White text on a black bar marks the one thing that is chosen or is news.
Say less. Interface text is short and standard: "Save", "Remove", "Not set up". A label that needs a sentence of explanation is the wrong label.

Memory

Code is the scarce resource, not data. A byte of code that runs costs four bytes of the interpreter's 64 KB; a byte of data costs one of a page that is mostly empty. Prefer a table to a chain of if, the kit to drawing by hand, the host's pick to a parser, time_text() to a calendar of one's own.
Keep small helpers out of line when they are called from many places - __attribute__((noinline)) - and let the build's report tell whether it helped.
Pictures as bits. In pictures/, never as strings in the source; large ones in files/.
Never hold an answer whole. Read it as it comes and keep what will be shown. For a working buffer use app_alloc() and give it back with a mark.

State and time

Every instance may be the last. Anything that matters is in the store before app_on_terminate() returns. Test by opening the application, leaving it and opening it again: it must look the same.
Keep what is shown until something better has arrived whole. A failed or interrupted request is not a reason to show an empty screen in place of an hour-old forecast.
Say why there is nothing. An empty screen is a bug. "Not set up", "No network", "Loading" are one call: ui_reason().
The clock may not be known, and may jump. Handle time_now() == 0. Use alarm_set() for "in ten minutes" and alarm_set_at() for "at seven".

The user

Nobody types on four buttons. Whatever needs text - a token, an address, a city - is a setting in the manifest, edited on the device's page. On the device a value is one of a few, stepped through with UP and DOWN.
Take the screen rarely. A notification for what the user asked to be told - a timer, a meeting. Never for what can wait until they look.
The user's data goes to the user's servers. List only the hosts the application needs. A server of the user's own is a url setting, not a host in the manifest; a token is a secret, sent by the host in a header the code never sees.
Ask the network no more than the data changes. Give the pace to the user as a setting with a sensible default. On battery the host will not fetch more often than every five minutes whatever is asked.

15. Publishing

A device installs from catalogs: folders of static files with an index, on any hosting that serves HTTPS - a git host's raw files, a static site.

tools/catalog/mkcatalog.py my-apps --out catalog       # builds every application of the folder
                                                       # catalog/catalog.json and a folder for each
  • The index lists each application's name, title, version, icon, and its files with their sizes and SHA-256. The device takes a file only when both match.
  • There are no signatures. What vouches for an application is HTTPS to a source the user chose; what contains it is the sandbox.
  • The official catalog is the perinkpheral-apps repository: it is the first source of every device. A user adds up to three more on the device's page - the address of a repository is enough.
  • The page shows a user what an installed application is, from its manifest: where it connects, how often, what it keeps, whether it starts with the device.
  • Bump version with every change: it is how a device knows there is an update.
