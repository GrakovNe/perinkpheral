# perINKpheral

A desk e-paper display built on ESP32-C6, with four buttons. Its software is a specialized operating system for e-paper, built on FreeRTOS/ESP-IDF. Perinkpheral OS runs WebAssembly applications installed from a catalog without reflashing the firmware.

The name is written `perinkpheral` in code, the repository and the domain; `perINKpheral` in the README, the logo and headings. The pun: peripheral vision + peripheral device + ink. The operating system is named **Perinkpheral OS** in both English and Russian. Use that name in prose instead of "host" when referring to the operating system. Network hosts, computer-side tests and existing API identifiers keep their technical names.

This file defines the vision, architecture, conventions, milestones and current state. Next to it are only references: `AGENTS.md` - the bench, build and flash recipes, what must not be touched in the driver; `hardware/README.md` - everything found out about the panel, with the datasheet and links; `SECURITY.md` - who could take what from the device, what stands in the way and what does not; `CHANGES.md` - what each release brings, its notes on GitHub, in the flasher and on the device's page. `docs/testing/stability.md` - the plan of stability testing: a soak on the device, fuzzing, a monkey in the simulator, a loss of power. Where they disagree, this file wins.

**Everything in this project is written strictly in English**: code, comments, commits, documentation, this file, the device's web page. What is translated is translated beside an English original, which is the one that is right when the two differ: the application guide's Russian (`docs/guide/source/guide.ru.txt`, built into `perinkpheral-app-guide.ru.pdf`; the owner, 2026-11-14), and what the device says - Perinkpheral OS's own words (`firmware/components/words/words.c`) and the strings of an application (`strings/<language>.json`), in English and Russian today. Names are never translated (E-Ink, SDK, Watchdog, the calls and constants). The firmware's fonts carry ASCII; letters beyond it come in glyph packs, and what has no glyph is spelled in ASCII (see "Text is bytes").

## Vision and philosophy

**Vision.** A separate screen for the desk that is not a second monitor: it can be ignored until it is needed and read out of the corner of the eye - a line of the schedule, the current track. In one phrase: a TRMNL without the server and with buttons. The goal is an extensible operating system with its own applets on hardware anyone can repeat, and a community of builders and application developers.

**Principles**, in the order they win arguments:
1. **Peripheral, not a monitor.** No backlight, nothing that moves, nothing that asks for attention. The device is silent until it is looked at, and what it shows is readable at a glance. This is why it is e-ink and why the refresh policy is conservative.
2. **Not a thin client.** The device does the work itself: it fetches the data, runs the application and draws the frame. No server prepares pictures for it, the vendor's or the user's own.
3. **The user's data stays the user's.** Showing a calendar must not require binding an account to a machine the user does not own. Requests go from the device straight to the source; there is no cloud of ours in between and there never will be.
4. **It has buttons.** A companion is something you can answer, not a picture frame: applications react to presses, and the user is always one long press away from taking the screen back.
5. **Autonomous.** It supports battery operation and charges over USB-C; it does not need a cable, a hub or a computer next to it.
6. **Cheap to repeat.** Common DIY parts, no custom PCB, and a case intended for FDM printing in PLA, PETG or ABS, with optional TPU feet. If a choice makes the device harder to build at home, it needs a very good reason.
7. **The user decides what is on the screen.** Not a fixed set of dashboards: an SDK and applets that anyone can write and install without reflashing. Perinkpheral OS provides shared services; applications define the content and interactions.

What follows from this: no backend of our own, no accounts, no telemetry; a static catalog instead of a store service; TRMNL compatibility as one application, not as the platform; project code under MIT, with separate licenses retained for fonts and dependencies.

### Wiring
```
Display → XIAO
  VCC  → 3V3
  GND  → GND
  DIN  → D10 (GPIO18, MOSI)
  CLK  → D8  (GPIO19, SCK)
  CS   → D7  (GPIO17)
  DC   → D5  (GPIO23)
  RST  → D4  (GPIO22)
  BUSY → D6  (GPIO16)

Button module → XIAO
  V → 3V3
  G → GND
  1 → D0 (GPIO0)
  2 → D1 (GPIO1)
  3 → D2 (GPIO2)
  4 → D3 (GPIO21)

Battery → XIAO
  BAT+ → BAT+ pad (bottom, next to "D5")
  BAT- → BAT- pad (bottom, next to "D8")

Free: D9 (GPIO20, MISO - the display does not need it).
```
The wiring is fixed and done - do not change it. Battery voltage and USB supply voltage are **not measured** - decided, do not propose dividers or ADC. The power profile is a Perinkpheral OS setting. Auto uses the existing USB Serial/JTAG connection to a USB host; this does not detect a charger or tell which source powers the board.

### Board specifics worth knowing
- Not on the header and not to be touched: GPIO9 (BOOT, strapping), GPIO15 (user LED), GPIO12/13 (USB D-/D+), GPIO3 and GPIO14 (the antenna switch - driven only by `firmware/components/board`).
- Antenna: at start GPIO3 → LOW (enables the RF switch), GPIO14 → LOW (ceramic) or HIGH (external U.FL). Without this Wi-Fi may work poorly. Done by `firmware/components/board`, the choice is `APP_ANTENNA_EXTERNAL` in menuconfig.
- GPIO16/GPIO17 are the chip's UART0 TX/RX, here they are the display's BUSY and CS. The console is on USB-JTAG only. The ROM bootloader still prints its boot log into GPIO16 at every reset (tens of ms) - no panel failure was observed on this bench.
- GPIO0-2 are the LP group: the buttons are on them, the display stays off them.
- **The way out when the main firmware has stopped answering: buttons 1 and 4 (UP and BACK) held together for ten seconds restart it.** The press is an interrupt and the ten seconds are counted by a timer whose callback runs in an interrupt (`firmware/components/input/buttons.c`), so it does not wait for the main event loop, the buttons' task or the scheduler; interrupts turned off for good are ended by the interrupt watchdog, as always. Nothing on the screen offers it - it is for when the screen cannot; Settings has Restart for when it can. Recovery reads OK and BACK directly and does not run this interrupt-based rescue combination. Written and built; **not tried on the device**: the development tools press buttons above the pins, so only a hand can.
- From light sleep any of the four buttons wakes the device (`gpio_wakeup_enable`). Deep sleep - not used in version 1 - is another matter: its wake-up on the C6 is ext1 on GPIO0-7 only, so buttons 1-3 would wake the device and **button 4 (GPIO21) would not**.
- Flashing over the native USB Serial/JTAG (`/dev/ttyACM*` on Linux, `/dev/cu.usbmodem*` on macOS), `idf.py flash`. Entering the bootloader: hold BOOT while powering up or resetting.
- 3V3 gives up to ~700 mA for everything. On battery the 5V pin is empty.
- Over-discharge protection is entirely the battery's PCM. Charge level and power source are not shown on the screen - there is no data.
- Charge LED: blinks while charging, off when full. The CHRG signal is not routed to a GPIO.

## Stack
- ESP-IDF 5.5, C. No Arduino, ESPHome, LVGL, GxEPD2.
- Application runtime: **wasm3** v0.9.0 (interpreter, sandbox). Applications are built with wasi-sdk (found through `WASI_SDK_PATH`; verified with 34); the firmware build needs it too, since the image carries applications.
- **Firmware and SDK tools share one Kotlin implementation** (the owner, 2026-11-15: "not two toolchains"). `tools/core` owns the contract reader, package formats, build flags, catalogs, device client and simulator network; `tools/cli` exposes them through `tools/perinkpheral` and holds the generators. The CLion plugin uses the same core. Java 21 or later; the launcher builds the jar with Gradle when its sources change. `flags` supplies the same compiler flags to CMake and the plugin; `headers` permits incomplete translations while editing, which `build` refuses. **Firmware and SDK generators and checks stay in Kotlin** (the owner, 2026-11-17). ESP-IDF's Python and the separate Home Assistant integration are outside that toolchain. The enclosure exporter in `tools/case`, added on 2026-11-18, is a separate Python 3.12 CAD utility for STEP/3MF geometry; it is not a replacement for `tools/core` or `tools/cli`. External tools: a C compiler for preview and simulation, ffmpeg for video, Chromium and poppler for PDFs.
- Fonts: the square one (code, `font_square.c`) for the logo; for everything else one of two families, the user's choice (`font` in the settings; Font in Settings on the device, and on the page). **Departure Mono**, a monospaced pixel font and what a device starts with: one bitmap of it at its own 11 px from `tools/perinkpheral font`, drawn at whole multiples - 22 px for Perinkpheral OS, and 11, 22, 33, 44, 66 and 110 px for applications. **Jersey**, heavier, its letters of their own widths: four faces of it, each drawn for capitals of so many pixels - Jersey 10, 15, 20 and 25 - rasterized on their own grids and picked so that the capitals of every size are as tall as Departure Mono's (10, 15, 25, 30, 50, 80 px for its 8, 16, 24, 32, 48, 80), so what is laid out for one family holds for the other. Applications ask for a size by its id and get it in the family chosen. The fonts are ASCII; the letters beyond it come in glyph packs.
- FS: LittleFS (partition `apps`, 640 KB). NVS twice: Perinkpheral OS's settings in the partition `nvs`, the applications' `kv_*` in one of their own, `appkv` (56 KB), so that nothing an application keeps can crowd the settings.
- Network: `esp_http_client` (TLS through mbedTLS), `esp_http_server` for the web UI.
- The display driver is our own: init, full refresh (and Waveshare's fast one), partial refresh of a window, panel deep sleep. The bytes are clocked out by hand over GPIO, as a SPI master in mode 0 would, with **CS toggled per byte** - otherwise the refresh never finishes (see `AGENTS.md`). The SPI driver of ESP-IDF sent the same and spent 17 of every 21 microseconds getting ready for a byte; by hand a byte is 8.
- Buttons: `gpio_config` input without the internal pull-up (the pull-up is on the module), active LOW, debounce 20 ms. A press is reported as it happens (down, up) and as what it meant (short, or long at ≥600 ms).

## Memory budget (the hard limit of the C6)
- SRAM 512 KB, shared by Perinkpheral OS, the application area, Wi-Fi and TLS. There is no PSRAM and there will be none.
- Flash 4 MB: `appkv` 56 KB, a factory recovery image of `0xE0000` (896 KiB) and one `ota_0` slot of `0x200000` (2 MiB), `appcode` 320 KB, LittleFS `apps` 640 KB and `glyphs` 64 KB (`firmware/partitions.csv`). Main must fit `ota_0`; recovery must fit `factory`. Builds check both independently. Both firmware builds use `-Os`; the release has no development tools (`sdkconfig.release`). The web page is gzip-compressed. CI reports image and RAM sizes against the preceding successful build of `main`. The partition table cannot change over the air.
- A wasm application's arena is **exactly 64 KB** (one wasm page, there is nothing smaller), fixed for everyone. Build: `-Wl,--initial-memory=65536 -Wl,--max-memory=65536 -Wl,-z,stack-size=8192` (`tools/perinkpheral build` does it); the interpreter is built with a limit of one page, so a module that asks for more does not load and none can grow.
- **One** wasm instance is loaded at a time. Background delivery unloads the scene, loads the owner and delivers the answer, then restores the scene unless the owner takes the screen. Its session survives this swap.
- **Sockets are counted** (`web_server.c`): lwIP has 12; the web server keeps three of its own, the setup access point's name server one, the poller one for the request it makes; the page's connections are the seven left, the oldest closed for the next. Promised more than are left, a connection finds no socket while the server still has room, nothing is closed and the page is dead (seen 2026-11-17, "error in accept (23)").
- **Heap admission** (`firmware/main/memory.c`). Wasm memory and interpreter allocations use the application area. Perinkpheral OS services allocate separately: a network session requires 60 KB free and a 17 KB contiguous block; a web response requires 24 KB and 8 KB; a firmware upload requires 32 KB and 8 KB. A refused web request returns `503` with "Not enough memory." Applications receive `HOST_FAILED_NO_MEMORY` after waiting up to six seconds. Catalog reads and app installs retry explicit memory/busy refusals and interrupted downloads up to three times, after 2, 4 and 8 seconds. Exhausted retries say "Device busy. Try again shortly." Lost responses and permanent refusals are not replayed: a lost response may follow a committed installation. Critical pressure means less than 12 KB free, a contiguous block below 4 KB, or a new allocation failure. The first check closes web connections; three consecutive checks, five seconds apart, trigger an orderly restart. A ten-minute period of session memory refusals also triggers a restart. Observing enough total and contiguous memory clears that period even if the next poll is not yet due. `/api/status` counts refusals and failed allocations.
- The application area is 128 KB: one 64 KB wasm page and 64 KB for the interpreter. Perinkpheral OS keeps the rest of the heap. Wi-Fi buffers are bounded in `sdkconfig.defaults`; IPv6 is disabled. Current free heap, its low-water mark and its largest block are reported by `/api/status`; bench measurements from older builds are not a memory budget.
- An HTTP response body that is not picked goes to the application as a stream, in pieces of up to 1 KB, while TLS is open; Perinkpheral OS never holds it whole. The 128 KB application area above is reserved at startup, independently of how much an instance uses; TLS and Perinkpheral OS need room outside it.
- Two frames of 400×300×1 bit = 15 KB each: the back buffer Perinkpheral OS draws into and the display service's copy of what the panel shows.

## Architecture

FreeRTOS/ESP-IDF provides the native task scheduler and low-level system services.
perINKpheral manages applications and their shared API, screen, storage and network
access. One WebAssembly instance runs at a time; background responses load their
owning application and then restore the scene.

### Application
**Feature freeze until the public release** (the owner, 2026-11-20): bugs, UI/UX and the polish of applications only; no new call, application or mechanism. The order to the release: manual acceptance (`docs/testing/acceptance.md`), fixes, the endurance run (`docs/testing/stability.md`), fixes, load testing (`docs/testing/load.md`), the release - at which ABI 3 is frozen in fact. The last feature in is the BACK chord of 0.1.63.

**ABI 3 is the application contract; its first firmware is 0.1.30.** The supported set is explicitly `{3}`; ABI 2 is refused with "Update the app.", with no adapters. The manifest's ABI is retained through parsing into `app_load()`, which selects the supported contract before running code. Firmware releases and ABI generations are independent. An existing name, signature, privilege, binary layout, constant, accepted input or observable meaning cannot change within ABI 3. A changed signature or meaning requires a new ABI while Perinkpheral OS retains the frozen generations it supports; additions after the 0.1.30 ABI floor carry permanent `HOST_SINCE_<name>` introduction stamps. New flags, exports or manifest behaviour that cannot be inferred from imports require an explicit firmware minimum. A new fixed struct layout needs a new call/type; `answer_info` alone permits extension after its unchanged prefix.

`tools/perinkpheral contract snapshot` records `sdk/abi/3.txt`; `contract check`, run by the host tests and CI, refuses removal or alteration of a recorded entry and an entry of the contract that is not recorded; an addition is recorded with `contract snapshot`. Until the first public release the owner may still break ABI 3 (2026-11-20: "we are moving to production, not there yet"): `contract snapshot --unfrozen` rewrites recorded entries, and is not used after it. It checks actual wasm32 sizes, alignment, field types and offsets with wasi-sdk, plus names, wasm function types, privileges, constants and introduction stamps. Snapshot writes also refuse to replace an existing entry. Package hashes are recorded separately in `sdk/abi/3/fixtures.txt` and checked by the same command. The frozen Probe, Hello and Settings packages under `sdk/abi/3/`, their manifests and translations and Hello's four-byte little-endian saved count are test inputs, never rebuilt by tests. The build checks the actual import and export types against the contract. The device page uses one ABI-and-firmware predicate for Install, Update and Update all; `/api/status.supported_abis` is the exact supported set. Downloaded manifests remain authoritative.

`/apps/<name>/manifest.json` and the application's files on the LittleFS partition; its module, `app.wasm`, arrives there and is moved into the code partition (see Memory). **`firmware` is the minimum compatible firmware version** (the owner, 2026-11-16): the build (`tools/perinkpheral build`) writes the latest firmware among the calls the module makes - `HOST_SINCE_<call>` in `sdk/host_api.h`, a permanent line for every added call after the first firmware, `HOST_FIRMWARE_FIRST` for the rest - and takes the maximum of those stamps, the ABI floor (`HOST_ABI_3_FIRMWARE_FIRST`, 0.1.30, the first firmware of abi 3), and an explicit manifest minimum for behaviour rather than a call; the catalog's index carries it. A rebuilt catalog asks no more of a firmware than its applications' calls do (the owner, 2026-11-17: stamping the SDK's own version raised every application with every release - a bug). `VERSION` at the root of the repository is the least version of the next release: CI releases the greater of it and the last release with its patch one up, so it is raised by hand only for a new minor or major version, or for a call whose `HOST_SINCE_` needs a version no release has yet - none may be past it. Perinkpheral OS does not start an application made for a newer firmware ("Update the firmware.") and does not install one; the page offers neither its installing nor its update, and says which firmware it needs. Perinkpheral OS reads `name`, `title`, `version`, `abi`, `firmware`, `fullscreen`, `system`, `writes_files`, `icon`, `polls` (with `pick`), `hosts`, `settings`, `intents`, `companion` and `certificates`, checks each, and skips a key it does not know. A poll is an `http(s)` `url`, an `every` of 10 seconds to a day - a number, or `"{{key}}"` of a setting whose value is the pace as a person writes it ("15 min", "1 h"): the user's choice, taken by Perinkpheral OS with no code in the application - and up to four `headers`; there are at most four polls, and the application knows each by its number. `{{key}}` in a URL or a header value is replaced by the value stored under that key (`text_template.c`). `name` is 1-13 of `a-z`, `0-9`, `-`, `_`: it is the folder, the key in the catalog and, as `a.<name>`, the NVS namespace of the application's store, and it must be the folder's name. `title` is at most 23 characters. `description` - what the application does, in a line of up to 95 characters, translated as the title is - is the page's and the catalog's: Perinkpheral OS does not read it, the page shows it under the title in the Catalog (the index carries it, and every language's title and description of the package as `translations`) and in what an application is. **Texts a person reads are counted in characters** - a title, a setting's title, help and options - and have a byte limit of twice that value; the fields of the contract that hold such text have a room in bytes - a notice's line and the header's text 63, a cell's name and value 47 - whose character capacity depends on the UTF-8 encoding, and Perinkpheral OS cuts a text that is too long between characters, never inside one. The module is at most 48 KB (`MANIFEST_MODULE_MAX_BYTES`; the build (`tools/perinkpheral build`) refuses a larger one), in whole sectors of the code partition; what it has to fit when it runs is the application area (see Memory). The applications in `sdk/apps` are built and packed into the partition image with the firmware (`APP_BUNDLE_APPS`). A manifest example (the server address is a placeholder):
```json
{
  "name": "plex",
  "version": "0.1.0",
  "title": "Plex Now Playing",
  "polls": [
    { "url": "http://192.168.1.10:32400/status/sessions",
      "headers": { "Accept": "application/json", "X-Plex-Token": "{{token}}" },
      "every": 15 }
  ],
  "hosts": ["192.168.1.10"],
  "fullscreen": false,
  "settings": [
    { "key": "token", "type": "secret", "title": "Plex token" }
  ],
  "intents": ["started"],
  "icon": [
    "...........",
    ".#########.",
    ".#.......#.",
    ".#..#....#.",
    ".#..###..#.",
    ".#..####.#.",
    ".#..###..#.",
    ".#..#....#.",
    ".#.......#.",
    ".#########.",
    "..........."
  ],
  "abi": 3
}
```
**An application may bring an icon**, in its manifest and optional: `"icon"` is 11 rows of 11 characters, `#` for ink and `.` for paper - the form Perinkpheral OS's own icons have in the source, which a person can type, which follows the icon rules by construction and which scales. The device draws it beside the title in its menu, a cell two pixels; the web page draws it on the application's tile; a catalog's index carries it, so its icon is visible before installation.

**Settings are declared in the manifest, not by code**, the way Pebble did it with a companion page: nobody types a token with four buttons. Installed apps lists the installed applications; a gear opens a settings form drawn from the manifest without running the application. Catalog is a separate section. A field is a `text`, a `secret` (the page can write it and cannot read it back), a `number`, a `choice` from a list of `options`, a `toggle`, a `place`, a `url`, a `link` or a `list` (items of up to 63 characters, as many as the value holds, stored with a line break between them, added and removed by the row on the page; its `default` is a list); it has a `key`, a `title` and may have a `help` line, a `default` and `"hidden": true` - for a setting something else writes, an integration through `/api/apps/settings`, which the page's form leaves off (HA Companion's server and token, written by the Home Assistant integration) - what an absent setting reads as (the owner, 2026-11-15): `kv_get` returns it, `{{key}}` is it, the page shows it, and nothing is stored until the user saves. At most 8 of them, a value at most 255 bytes. A `url` is the address of the user's own server - `http://192.168.1.10:8123`, a scheme and a host and maybe a port, nothing after - and the one setting a poll's URL may begin with and `hosts` may name: `"url": "{{server}}/api/states"`, `"hosts": ["{{server}}"]`. That is how an application for Plex or Home Assistant is written once for everybody's server. A `{{server}}` entry authorizes that configured host; other destinations must be declared separately. Changing the server clears secrets that were not supplied with the change. The `url` setting is the user's to write and the application's only to read: `kv_set` on it is refused, or an application could move its own server - and the token with it - wherever it liked. A value that goes into a header or stands as the server is looked at again when it is used, whoever stored it: one with a carriage return in it fails the request, and a list's line breaks become commas: `{{key}}` of a list is its items, joined with commas, each encoded in a URL and as it is in a header. A `link` is a whole address the user was given - a calendar's secret `https://host/path?key` - and is the whole of a poll's URL (`"url": "{{feed}}"`, `"hosts": ["{{feed}}"]`): a `{{feed}}` entry authorizes the configured host; other destinations must be declared separately. Like `url`, the setting is writable by the user and read-only to the application; the page takes `webcal://` for `https://`. A public manifest default may be shown as text; a custom stored link is returned only as set or not set. An empty setting saved through the web API overrides the default; `kv_set(..., 0)` deletes the key and restores it. A `place` is asked for by its name: the page offers places as the name is typed (the browser asks Photon, a search of OpenStreetMap; the device does not) and fills the two `number` settings the place names as its `latitude` and `longitude`, which it does not show. The values are stored in the application's own store under the keys the manifest names, so the code reads a setting with `kv_get` by the same key, and Perinkpheral OS substitutes it into URLs and headers (`{{key}}`). A change arrives as `app_on_settings()`; an application that is not on the screen is loaded for the call and unloaded after it, as for data.

**The developer supplies translations; Perinkpheral OS loads the selected language.** An application's `strings` folder holds a file a language - `en.json`, `ru.json`, each an object of the same keys; the build (`tools/perinkpheral build`) makes `strings.h` of them (`STR_NO_EVENTS`, `app_string(id)`), builds English into the module and writes a table for every other language beside it (`strings.ru`, a file of the application's). When an instance is loaded Perinkpheral OS copies the table of the device's language (`language` in the settings; Language on the page) over the English one in the application's memory - when there is one, it is sound and it fits; else the application speaks English - so reading a string costs the application no code and no call. `text_fill` puts arguments into `{0}`, `{1}` of a pattern, in whatever order the language has them. The build fails on a language the system does not know (`sdk/languages.json`: the languages, and the glyph packs each needs), on a translation that lacks a key or has one too many, and on a letter the language's glyphs do not have. No plural forms. **What of the manifest a person reads** - the title, a setting's title and help, the labels of a choice's options - is translated in the same file under the key `manifest`, held by the build to the manifest itself and written beside it (`manifest.ru`); Perinkpheral OS takes the title from it for the menu, and gives the page the settings in the device's language, an option keeping its value and gaining a label. **Perinkpheral OS's own words** - what the buttons of its notices do and of the picker and the date-and-time screens (`ui_draw_picker`, `ui_draw_date` with no words of the application's: Save, Next, Back, Cancel), its questions, why an application has nothing to show, the names of days and months - are one table (`firmware/components/words/words.c`), English and Russian, in the firmware. Every application of the catalog has Russian but `badapple`, whose video leaves its files no block for a table. The system applications have Russian too: they have no files, so their tables are embedded in the firmware beside them (`launcher_system_file`). The device's page speaks the device's language too, in the same terms (`firmware/main/web/js/i18n.js`: a word of the page and its Russian, the device's answers among them; whole texts are put into the language where they stand, texts made of parts through `t()`); the page remembers the language in the browser and is read anew when the device says another. The cities a time zone is chosen by are one list, `firmware/system/settings/cities.json` - each city's English name, its Russian, its POSIX zone and the IANA names a browser may give it: `tools/perinkpheral cities` makes Settings' `cities.h` of it (the host tests hold the two together), the page carries it (`<!-- data: -->`; the device's limits - how many applications and sources, a setting's length - come from the firmware's headers the same way, `<!-- defines: -->`), and both show the cities in the device's language, sorted by the names shown; the city chosen is Perinkpheral OS's setting `tz_city`, so the device and the page show the same one of those that share a zone. Still English: what the crash record and the build say of themselves.

**A companion page** is for what a form cannot do - signing the user in somewhere, choosing from what is there. `"companion"` in the manifest is its address, `https` only: a static page of the application's author on any hosting. The device's page opens it in a window from the application's settings (Set up), and the two talk in messages: the companion says it is ready, gets the application's settings and what is set (no secrets), and hands back values for keys the manifest declares; they go into the form, and the user saves them. Nothing of it runs on the device and nothing passes through a server of the project's. `sdk/companion/example.html` is a sample. The form accepts companion results only for fields present in it; hidden settings have no field and are written through `/api/apps/settings`. Secret and link values are omitted from the message sent to the companion.

**Manifest polls can use Perinkpheral OS JSON picker.** A poll declares paths such as `current.temperature_2m` or `daily.weather_code[0]` in `pick`; Perinkpheral OS extracts their values and delivers `app_on_picked`. Polls without `pick` and explicit HTTP requests deliver chunks through `app_on_data` for the application to parse. The picker is one source, `sdk/lib/json_pick.c`, built into Perinkpheral OS and into any application that wants it: an answer to a request of an application's own comes in pieces, and the application feeds them to a picker of its own. Ease of writing an application is worth Perinkpheral OS's memory here. A path may have `[*]` in place of one index - `close[*]` - for every element of an array, kept as text in a buffer of 8 KB Perinkpheral OS takes for the answer and gives back after it (`HOST_LIST_BYTES`); `app_value_series()` turns them into a series for `ui_draw_chart`. Numbers with decimals are `sdk/lib/app_fixed.h`: integers of 64 bits with so many decimals, read from text with an exponent, divided and written with rounding half away from zero.

**HTTPS** verifies servers against the root bundle carried by ESP-IDF. An application may bring up to two certificate-authority roots in its package, PEM or DER, at most 4 KB each (the owner, 2026-11-15). The build checks that each is a currently valid authority certificate. The poller adds them to the browser root set for that application only; the page asks about them before installation. A self-signed server certificate is not an authority root. The owner decided on 2026-11-12 that a user-supplied server certificate belongs in an application setting and must trust only that application's hosts. That setting is not implemented.

Response headers beyond `answer_info` are available through `answer_header` (firmware 0.1.51).
Perinkpheral OS retains up to 1024 bytes of names and values for the active response;
repeated fields are separate. If the complete set does not fit, every `answer_header`
call returns `HOST_ERR_NO_SPACE`; `answer_info` remains available. Undersized output
buffers also fail without truncating credentials. Redirects discard previous headers.
Applications implement authentication themselves and can keep a small session in their own
KV store when it changes. Scene/session RAM is not a background credential store.

### System applications and the system API
Perinkpheral OS's own pages are applications too - written with the same SDK, run by the same interpreter - so that Perinkpheral OS is built with what it gives to others. They are **system applications**: built from `firmware/system`, carried inside the firmware image (an update over the network brings them along, so they always speak the API of Perinkpheral OS they run on), never installed and never removed, and not counted among the installed ones. Their names begin with `sys.`, which no installed application's name can. `Settings`, `About` and the setup screen are bundled. `Settings` is the device's settings with four buttons and no keyboard: General (date and time - from the network or by hand, the time zone by a city from a list, power saving: Disabled, Always or Auto; the default application and how long the menu waits before giving it the screen), Apps (the installed ones, each can be removed), Display (the font - Departure Mono or Jersey - the three numbers of the refresh policy, Fast refresh and the clock in the header), Wi-Fi (the network, the address, forgetting it), Buttons (what holding one does - BACK the menu, OK in the menu a move, UP or DOWN a page, UP and BACK ten seconds a restart - since nothing on the screen says it), Restart and Reset - each of the last two a question. A value is changed on a page of its own with Save and Cancel (the picker); a long choice - the time zone's city, the default application - is a list with a check on what is set. Nothing is typed: a value is one of a few stepped through with UP and DOWN, a date is its parts stepped the same way with OK to the next and BACK to the one before, and what cannot be undone asks first. What needs text is set from the web page. `About` is what the device is, on two pages that OK turns between. The first is the mark, the version of the build (`v0.1.0-0adbfb4`: the version the project is at and the commit), a QR code of the project's address and, in the small font at the bottom, the author and the license; it is the splash too. The second is the device's state - its name, its network and address, the firmware version, free RAM, free flash for applications and free room of their stores, and uptime, all asked of Perinkpheral OS with `sys_info`.

What stays native is what has to work when nothing else does: the menu, the message of an application that crashed, the question about a storage that cannot be read and the question a request from the network waits on. The screen that says how to give the device a network is a system application too (`setup`, not in the menu): without it the device starts at the menu, and About has the address. The splash at power-up is not among them: it is About's picture, and without it the device simply starts.

They are written with the **system API**, the `sys_*` part of `sdk/host_api.h` (`sys_info`: the version, the name, the network and its state, the address, the slot, what is free of RAM, of the flash for applications and of their stores; `sys_setting_get` / `sys_setting_set` / `sys_setting_range`: only the explicit page-visible keys documented in `sdk/host/sys.h`, with internal and unknown keys returning `HOST_ERR_NOT_FOUND` for all three calls; `sys_time_set`; `sys_app_list`, `sys_app_title` / `sys_app_remove` (HOST_OK queues one removal after the handler returns; a second returns HOST_ERR_NO_SPACE); `sys_app_get_default` / `sys_app_set_default`; `sys_run`: restart, forget the network, factory reset; `sys_draw_logo`, `sys_logo_width` / `sys_logo_height`). It is not fenced off: the device is its owner's, and any application may have it. It has to ask - `"system": true` in its manifest - and the page says "<title> requests system access." before it installs one. A module that imports a `sys_*` call without having asked is refused by the build (`tools/perinkpheral build`) and by Perinkpheral OS.

### Execution model
- **Scene** - one application, it owns the screen and the buttons.
- **Polling** - Perinkpheral OS itself fetches every `polls` entry of every installed application at its `every`. This is the background mechanism ("pushes").
- **A poll over a list** (the owner, 2026-11-15: "one common list"): `"each": "<list setting key>"` sends one request per item, one at a time between other work. `answer_item()` identifies it. A `prefix` poll claims matching items and substitutes them without the prefix; a poll without a prefix takes the items no prefixed poll claims. Up to 16 requests per application may wait in the queue.
- **Queued credentials and destinations** - the expanded URL is queued unchanged. Immediately before sending, the main event loop reauthorizes it against current application KV values and fills all headers in that same operation, with no settings save or application write interleaved. A changed url/link setting can make the old destination fail with `HOST_FAILED_NOT_ALLOWED`; it is never silently retargeted. Once prepared, the request keeps that snapshot through transmission. Templates read any application KV key, including undeclared ones, with manifest defaults for absent declared settings.
- **Raw requests** - an application may itself call `http_send` (method, URL, headers, body) - for OAuth, calendars, actions on a button. Requests go into Perinkpheral OS's queue, one at a time for the device; an application has up to 16 waiting (`HOST_HTTP_PENDING_MAX`) and queues more as answers come, the applications taking turns and polls taking turns with requests; the queue lives on the heap, 16 KB at most for the device. Only hosts from the manifest's `hosts` are allowed. The response arrives through the same `app_on_data`; an interrupted one is dropped, not repeated.
- **Redirects** - a `GET` that is answered with one is asked again where it says, up to three times. A request of the application's own stays inside its `hosts`: sent elsewhere, it fails with `HOST_FAILED_NOT_ALLOWED`. The headers an application gave do not travel to another host; `http` and `https` of one name are one host, and so is a port written out when it is the scheme's own. A request of another method is not sent twice: its redirect is the answer.
- **Delivery** - Perinkpheral OS calls `app_on_data(request, ptr, len, flags, http_status)` in chunks (flags: FIRST, LAST, FAILED; the HTTP status comes with the first chunk) on the owning application, **whether it is on the scene or not**:
  - on the scene - the call is made right away;
  - not on the scene - unload the scene (`app_on_blur`) → load the owner → deliver → if it called `screen_request()` it is opened as the scene - anew, from what it stored - otherwise unload it and bring the previous scene back (`app_on_focus`).
- **Install and update notifications** - loading must succeed before the notification is consumed, then it is consumed before its callback, including a missing or trapping callback and an instance stopped by `app_on_load`. A load failure stays pending until the next startup or application-list reload. "Updated" means a different module-and-manifest package id, regardless of version strings.
- **State** - Every application must restore itself from `kv_*`: Perinkpheral OS unloads it on every scene change and background delivery. **Where the user is** - a page, a row, a value half set - is not worth a write of the flash and goes into the session (`session_set` / `session_get`, up to 1024 bytes of RAM allocated when first set, held by the scene; the one mechanism since 0.1.61 - `scene_state_*` was removed, and an application that keeps more than 128 bytes names firmware 0.1.61): kept while the application is in the stack, across its unloads, and gone when it leaves the stack (BACK from its first page, `screen_leave`, a long BACK, too many above it), when it is opened anew from the menu, and at a restart. Saved in `app_on_blur`, read in `app_on_focus`; an instance loaded off the screen only reads it. `app_session_save` / `app_session_load` in `sdk/lib/app_state.h` keep one struct that way. Settings, Calendar and HA keep theirs. The framebuffer is not touched during the swap (the screen is not redrawn); an application's timers (`timer_set`) stop when it leaves the screen and are set again by it in `app_on_focus`.
- **Buttons** - the layout is the same everywhere in Perinkpheral OS: 1 up, 2 ok, 3 down, 4 back. Applications are encouraged to keep it.
- **Navigation uses a stack** (`firmware/components/ui/wm.c`, pure). The menu is under everything and is what shows when the stack is empty. A long press on BACK is the beginning again: the stack is emptied and the menu shows, and BACK in the menu does nothing - unless the user chose a default application, which BACK in the menu then opens. Whatever takes the screen goes on top - an application opened from the menu, a question Perinkpheral OS asks, an application whose alarm came - and the one under it leaves and waits; when the top is done, what was under it enters again. BACK is one step down. Opening from the menu starts anew; a scene is in the stack once - opened again, it moves to the top from where it waited; six deep, the oldest forgotten. Only the top is loaded - there is room for one application - so a scene that waits enters again from what it stored. Nobody keeps a "where to return" of their own: Perinkpheral OS's question and its work notice are entries like any other. **BACK is the way out and needs no code**: a short press of BACK leaves an application that does not export `app_on_back()` - to the menu, when it was opened there. One with pages of its own exports `app_on_back()`, gets the press there instead of in `app_on_button`, goes a page back and calls `screen_leave()` from its first. An application counts on this: `screen_leave()` is one step down, and one that took the screen with `screen_request()` returns the user to what they were looking at.
- **Switching without the menu** (the owner, 2026-11-20): button 4 held and button 1 or 3 pressed opens the previous or the next application in the menu's order, round its ends, the system's pages passed over (`components/ui/back_switch.c`, pure; `scene_menu_neighbour`). It acts on the way down. The presses of such a chord reach no scene, and that hold of button 4 is neither BACK nor the way to the menu; a chord must begin within the long press's 600 ms. No application loses a handler: the long BACK was never theirs.
- **Switching** - long press on button 4 → Perinkpheral OS menu (list of applications, selection with buttons 1/3, confirmation with 2, button 4 opens the default application when there is one). A row of the menu is the application's icon and its title; the selected row is inverted, white on a black bar. **The menu's order is the user's** (the owner, 2026-11-16): a long press of OK takes the row to move - it stands in a frame, and along the bottom UP and DOWN at the sides and OK in the middle, the kit's own buttons with no words - UP and DOWN carry it a row and stop at the ends, OK keeps the order, and BACK, which the row does not name, puts the row back, as a long BACK does - in the menu the long press is the menu's own; whatever takes the screen meanwhile puts it back too. Every row moves, Settings and About among them. The order is kept by name in Perinkpheral OS's settings (`menu_order`, `menu_order.c`, pure), an application installed since comes first - one removed forgets its place, so it comes first when it is back - and the page shows its tiles in the same order. All other button events go to the application on the scene.
- **Preemption** - `screen_request()` from an application that received data in the background. Protection against a war for the screen: no more than one preemption per N seconds (30), whoever asks - there is no priority between applications; none within 30 seconds of a press of the user's, and none over a question waiting for its answer (what cannot wait is a `notification_post`); the decision is made after delivery ends, after the last piece of a streamed answer, and a refused request is discarded without retry; a long press on button 4 always returns control to the user, and the notices that wait show at the next press, not over the menu at once.

### Perinkpheral OS architecture
Perinkpheral OS is organized in layers. Each layer knows only the ones below it:

| Layer | Where | What it does |
|---|---|---|
| Drivers | `firmware/components/epd` (`epd.c`), `firmware/components/input`, `firmware/components/board` | the panel, the buttons, the antenna switch |
| Display service | `firmware/components/epd` (`display.c`, `refresh_policy.c`) | keeps a copy of the frame the panel shows; given a new frame it leaves the panel alone if nothing changed, refreshes it, or says "too soon" |
| Graphics | `firmware/components/gfx` | draws on a surface: the whole frame or a viewport into it with its own origin and clipping |
| Window manager | `firmware/components/ui` (`wm.c`) | which scene has the screen, how the user moves between scenes, how a frame is put together from the header and the scene's picture |
| Scenes | `firmware/main/scene_*.c`, `firmware/components/appsys/app_scene.c` | tie a model to a view and decide what the buttons do, all behind one interface (`scene.h`): enter, leave, button, draw |
| Views | `firmware/main/screens.c` | a struct in, pixels out; no hardware, rendered by `tools/preview` |
| Services | `firmware/main/sysinfo.c`, `firmware/main/status.c`, the settings' store, the poller (`firmware/main/poller.c`), `firmware/components/net` (Wi-Fi, the clock) | the data, with no idea that a screen exists |

- **A partial refresh sends only what changed.** The display service finds the box outside which the new frame is the frame on the panel (`frame_box.c`, pure) and the driver sends that window - Waveshare's own `PartialDisplay`, the same commands and waveform. The window is taken together with the one of the refresh before, so that the result does not depend on what the controller does with its two frames afterwards. After a partial refresh the panel is left out of deep sleep for 1.5 s (a deadline of the main event loop's puts it there), and one that comes in that time needs no reset. A step in the menu is 0.46 s, was 1.0 s; the whole frame 0.53 s: 0.41 s of BUSY and the bytes. Seen in the log only: the picture on the panel itself has to be looked at by a person.
- **A list stands still while the selection moves inside it** (`list_first_row`): its top row is kept - by the menu, by Settings for each page, by `app_list_first` for an application - and moves only as far as the selection needs to be seen, so a step does not move every label on a panel that takes half a second to show it. **A long UP or DOWN moves a page** of rows and stops at the ends, in the menu, in Settings and in `app_list_button`; in the date editor it steps a part far (minutes by ten, days by a week).
- **A list longer than the screen has a scroll bar** at its right edge (`firmware/components/ui/scrollbar.c`, pure): a thin line and a thumb on it - as much of the line as the rows shown are of the list, as far down as the first of them. The selected row is shorter by the bar's room. Perinkpheral OS's menu has it, and the lists of Settings draw the same. **A row's label and value never meet** (`list.c`): too wide together, a value of up to half the row - a time, a state - stays whole and the label is cut with `...`; a longer value has what the label leaves and never less than the half.
- **Two frames.** The back buffer (`host.c`) is where frames are put together; the display service holds the front copy of what the panel shows. Drawing never touches the panel, an unchanged frame costs no refresh, and a scene cannot spoil the screen halfway.
- **Layers are areas of one frame**, not buffers of their own: the header and the content do not overlap. A scene that is not full-screen gets a viewport under the header and cannot draw outside it.
- **A scene never refreshes anything.** It reports that its picture changed and draws when asked; the window manager passes on why the frame changed (a switch, a press, data), and the display service decides what the panel does.
- **One module keeps every deadline** (`firmware/components/deadlines`): the scene's timers, the applications' alarms and polls, the panel's sleep and its daily refresh, the while after a press, Wi-Fi's retries, the day turning in the header, the menu left idle, the device stopping. The table is pure (`deadline_table.c`); around it are one timer set for the nearest and the clock as the scale. Due deadlines are posted to the event queue and handled by the main event loop. If posting fails, the deadline remains due.
- **One event loop** (`events.c`). A press, later a timer or a response from the network, is posted from its own task and taken off by the main event loop one at a time: application handlers and scene changes are serialized in that loop. Service tasks run concurrently with published snapshots and their own locks.
- **The menu is a scene** like any other, not a layer over an application: opening it takes the screen away from whatever had it, which waits under it in the stack.
- **Priorities** (the model of 2026-11-14; in code it is one header, `firmware/components/board/include/priorities.h`, which every task takes its number from and which will not compile with the tiers out of order; a number is a FreeRTOS priority, the larger the sooner). What the user sees and touches comes before what is computed for them, and what keeps the radio alive comes before both:

  | Tier | Who | Priority | Why there |
  |---|---|---|---|
  | The radio and the network | Wi-Fi 23, the timer's task 22, system events 20, TCP/IP 18 - ESP-IDF's, not ours to move | 18-23 | late, they lose the connection |
  | Input | `buttons` | 10 | samples the pins for milliseconds; a press must be seen whatever else runs |
  | The screen | the main event loop (`host_run`, the main task) | 6 | draws the panel, runs the applications' handlers, answers presses |
  | Servers | the web server 5, `wifi` (the plan of connecting) 5 | 5 | a person may be waiting at a browser, but not at the device |
  | Background | `poller` 4, `ota-probation` 4, `captive_dns` 4 | 4 | a TLS handshake is seconds of arithmetic nobody watches |
  | The rest | the development console 2, mDNS 1, FreeRTOS timers 1, idle 0 | 0-2 | |

  Rules: a task that only computes goes under the main event loop; a new task is given its tier here before it is written; nothing of ours goes above 10.
  **Interrupts** are all of one level (1): the buttons' pins, the timer, the radio. A handler of ours does nothing but hand on - a semaphore, a count - and the one that counts the ten seconds of the rescue combination touches RAM only. Above them is the interrupt watchdog alone (300 ms). No critical section of ours is longer than the panel's reset pulse, 2 ms.
  **Events** have two queues, and the main event loop takes input first: presses (16) before everything other tasks ask of it (64). The others ask one thing at a time and wait for the answer, so nothing piles up before a press but the one call in hand; what a press does wait for is what the loop is in the middle of - a handler (3 s at most), a refresh (0.5 s, or 2.2 s for a full one).
- **Development tools** (`APP_DEV_CONSOLE`, on by default, off for a release): the device is driven and looked at without hands on it. Over the network, `/api/dev` gives the frame the panel shows, takes presses, opens an application and takes a new build of one; `tools/perinkpheral` is the command line for it, and `tools/perinkpheral run <app dir>` builds an application, uploads it, restarts the device and opens it without reflashing. `tools/perinkpheral serve <app dir>` is the same for a person in a browser tab beside any editor - the live screen, the four buttons (and the keyboard's arrows, Enter and Backspace), the log as it is written and a Run button; `tools/perinkpheral new <name>` makes an application to start from, and `log --follow` prints the log as it grows (`/api/log?since=<where the last answer ended>`, the end in `X-Log-End`), on across a restart: a device that was away is asked when it started, and its new log is read from the beginning. The page of `serve` takes requests from itself only, as the device's does: another site in the same browser could otherwise press the device's buttons through it. `tools/perinkpheral build` says what a build came to against what the device has: the module, the code and what running it takes of the interpreter's 64 KB, the data and the stack in the 64 KB page, the files. Over the cable, characters typed into the USB console do the same for a device with no network (`tools/perinkpheral usb <port>`). Whatever touches the frame or the scenes is handed to the main event loop through the event queue.

### Perinkpheral OS screens: notices
What Perinkpheral OS itself has to say takes the whole screen, with no header, and is one picture drawn after the owner's sketches (`notice_draw` in `firmware/components/ui/notice.c`, pure): two lines of large text on the left, a large icon from Perinkpheral OS's set on the right, and along the bottom either what the buttons do or three strokes that stand for work going on. No bar that moves. **The buttons are named the same way everywhere** (`kit_actions`): a button's name white on black - what OK does and then OK from the left edge, BACK and then what it does from the right: `Format OK        BACK Skip`. A button that is the only one stands in the middle. The icon stands a little in from the right edge.
- **A question** (`scene_confirm.c`): "Update firmware?" with the update icon, "Factory reset?" with the warning, "Join <network>?" with the signal, "Install system app?" with the gear. OK does it, BACK cancels; the menu and a minute of silence cancel too. A press is not an answer until the question is on the panel.
- **An error** (`scene_storage.c`): "Storage error" with the warning; OK formats, BACK goes on without.
- **Work going on** (`scene_working.c`): "Updating in progress" from the first byte of a firmware image to the restart into it, or until the upload is given up. The buttons do nothing.
- **A notification** (`scene_notify.c`, `notification_post` in the contract): what an application has to tell wherever the user has gone - the timer's "Time is up", the calendar's meeting that begins. The application hands Perinkpheral OS the notice from any handler, an alarm's above all, and is done: Perinkpheral OS shows it under the header over whatever has the screen, keeps it until OK or BACK dismisses it, and gives the screen back. Up to four wait their turn; a restart forgets them.
- **An application that is not running** (`app_scene.c`): its title, "crashed" or "cannot start", why in a line of ordinary text under them, the warning; a short press of any button closes it.
- **The questions Settings asks** - remove an application, forget the network, factory reset - are the same notice, drawn by Perinkpheral OS for the application (`ui_draw_notice`), under its header: OK does it, BACK cancels.
- **The kit** (`firmware/components/ui/kit.c`, `list.c`, `notice.c`, all pure, rendered by `tools/preview`) is what every screen is put together from, Perinkpheral OS's and an application's alike - the design system. Primitives: text in four styles (text, title, caption, value), the title of a page with its line, an icon in three sizes (22, 44, 99 px), a button with what it does, the row of buttons along the bottom. Elements: a value bar that changes only with its data, a chart (a series of numbers as a line, an area, bars or steps), the frame with arrows around what UP and DOWN change. the cell - a name, a picture and a value in a box of any size, which is what a dashboard is made of. Screens: the list (rows with values, options with a check, facts nobody chooses from), the notice (a question, an error, work going on, a message such as "Not set up"), the picker of one value from a row, the date and time set a part at a time. An application asks for them with `ui_*`; **what the buttons do on those screens is `sdk/lib/app_ui.h`** (`app_list_button`, `app_picker_button`, `app_date_button`, each answering changed, done or cancelled), so an application writes only what the result is for. Nobody has to use any of it: `gfx_*` draws anything. Settings is written with it, and `kit` in the catalog shows every part on a page of its own.
- **Any application may ask for Perinkpheral OS's look**: `ui_draw_notice` is this notice, and `ui_draw_list_row` a row of Perinkpheral OS's list - the bar behind the chosen row, a value or an icon at the right edge, the scroll bar (`firmware/components/ui/list.c`, pure). The menu and the lists of Settings are drawn by the same code, so an application that uses it looks the part and stays so when the look changes.

### Power-up
A partition of applications that cannot be read is not formatted without user confirmation: after the splash the device says "Storage" and "Storage error" with Format and Skip (`scene_storage.c`, native - it has to work when nothing else does). Skip leaves the device running with no installed applications; Format erases the partition and restarts. What the applications stored is in NVS and stays.

The splash moves on after its deadline or a press. A background delivery does not reset that deadline:
- **no network stored** - to the setup screen: the name of its access point and the address to open;
- **otherwise** - to the default application when the user chose one, else back to the application that was on the screen last (its name is kept in NVS), or to the menu when there was none.

A device on a shelf has to come back from a restart showing what it showed, without a press.

**The default application** (`default_app` in the settings, by name; General in Settings on the device, and on the page) is what the device shows by itself: after a restart, by BACK in the menu, and when the menu has been left alone for `menu_idle_min` minutes (1 to 60, 5 by default; `DEADLINE_MENU_IDLE`, set anew by every press). Only the menu gives way: an application that took the screen - by an alarm, say - has something to tell and stays until the user closes it. A default that is not installed is as none.

### Wi-Fi
- **No network stored** - the device starts an open access point named after itself (`Perinkpheral-XXXX`) and waits to be set up at `192.168.4.1`. The setup screen shows a QR code that joins a phone to that access point, with the network name and the address in words under it. A QR code cannot both join a network and open a page, so the access point is a captive portal: its name server (`captive_dns.c`) answers every name with the device, the web server redirects whatever it does not know to its page, and the phone may offer the setup page. Otherwise, open `http://192.168.4.1`. The name server answers only while the access point is up.
- **A network stored** - it connects; a lost or failed connection is tried again after 2, 4, 8 ... at most 30 seconds.
- **Two minutes without success** - rescue: the setup access point comes up as well and the device keeps trying once a minute, so a wrong password never needs the cable. Connected again, the access point goes away.
- The rules are `firmware/components/net/wifi_plan.c`, pure and host-tested; `wifi.c` only carries them out. The Wi-Fi library keeps nothing in flash: the credentials are Perinkpheral OS's settings.
- The device answers to its name: `perinkpheral-xxxx.local` (mDNS, the `espressif/mdns` component), and announces its page as `_http._tcp`. It costs about 8 KB of memory and 42 KB of the firmware.
- Time comes from SNTP whenever there is a network, in the user's time zone (a POSIX TZ string in the settings). Everything a person reads is local time: the header, the status page, the applications through `time_zone_offset()`. Until the first answer the device does not know the time: the header shows no date and `time_now()` is 0.

### Header
Perinkpheral OS draws a header above its own screens and above every application that does not ask for the full screen:
- On the left the Wi-Fi icon in one of two states - connected, or not connected (the same icon struck through). It shows the outcome of the last connection attempt, which is what matters in the profiles where Wi-Fi is off between polls.
- On the right the date (`Wed 11 Nov`), blank while the time is unknown.
- No application title or network name is added by Perinkpheral OS. The date changes once a day. There is no footer. **The time instead of the date** is a setting (`header_clock`, on by default since 2026-11-17; Display in Settings on the device, and on the page): the header then turns with every minute, above every application.
- **An application may put its own text into both**: beside the icon on the left, where Perinkpheral OS has nothing, and on the right in place of the date (`header_set_text`). It gives a line and nothing more - the font and the size are Perinkpheral OS's. A text that does not fit is cut with `...`, and the two never meet: when together they are too wide each is sure of half the width, and what one does not need of its half goes to the other (`wm_header_share`, `gfx_fit_text`). A side the application gave nothing for is Perinkpheral OS's; a text of one space leaves it empty. The texts are forgotten when the application leaves the screen. `weather` shows its city, behind a setting of its own.
- **An application may keep an icon and a line in the header while it is away** (`header_set_status`): something the user set going and wants in sight - the timer's minutes left and its hourglass. The header reads **icon text ... text icon**: on the left the icon stands in place of Perinkpheral OS's Wi-Fi one with the line after it, on the right the line stands in place of the date with the icon after it. They are there above every screen with a header, whoever is on it. A side is the application's that set it last, until it gives it back, is removed, or the device restarts; a side kept this way comes before what the application on the screen gave for it - on the right; the left says where the user is, and a page's own title there comes first, the kept status showing where the screen leaves the side to Perinkpheral OS. A recurring alarm (`alarm_set_every`) is what keeps the line right. `timer` keeps the right side.
- An application chooses in its manifest: `"fullscreen": false` (the default) leaves it 400×260 under the header, with its coordinates starting there, and it cannot draw over the header; `"fullscreen": true` gives it the whole 400×300. A long press on button 4 opens the menu in either mode.
- The network name and the address are on the second page of About, not in the header.

### Perinkpheral OS API (wasm imports)
The only contract is `sdk/host_api.h`, written by subject in `sdk/host/` - `base` (the macros, the return codes, the log, `HOST_LAYOUT`), `app` (the life's handlers, settings, the session, intents), `buttons`, `text` (strings, `text_fill`), `gfx`, `ui` (the kit), `screen` (drawing a frame, redraw, the header, the stack, notifications), `net`, `store` (the store and files), `time` (with alarms and timers), `sys` - which the umbrella includes and the tools read in that order. An application includes the umbrella and no file of `host/`: which declaration stands in which file is not the contract (the owner, 2026-11-20) and may change after the freeze; an entry added after the 0.1.30 ABI floor has its `HOST_SINCE_` stamp beside it, and every struct that crosses the boundary is held to its size on both sides (`HOST_LAYOUT`). Applications and Perinkpheral OS's import table are built from it, and the build (`tools/perinkpheral build`) refuses a module that imports anything else. Existing ABI 3 names, signatures, privileges, constants, layouts and meanings stay available. `HOST_API_VERSION` and the manifest's `abi` are 3; a changed signature or meaning requires a new ABI. Additions carry permanent `HOST_SINCE_<name>` stamps and preserve every recorded entry in `sdk/abi/3.txt`. ABI 2 is refused without adapters; its applications must be rebuilt for ABI 3. Commands name the subject then the verb (`kv_get`, `gfx_draw_text`); queries name the subject and what is asked (`gfx_width`, `time_now`); events Perinkpheral OS calls are `app_on_<what happened>` (`app_on_load`, `app_on_picked`). **Perinkpheral OS's icons** (`firmware/components/gfx/icons`, `HOST_ICON_*`): 49, including navigation, notices, weather, home, energy and air quality (`PARTICLES`, `POLLEN`, `GAS`, `DUST`, `LEAF`, `MASK`). Each has an 11-cell drawing; optional 22- and 44-cell drawings supply finer detail. Perinkpheral OS uses the finest drawing that fits at two pixels per cell or more. `gfx_icon_ink` measures the visible ink. `tools/perinkpheral icons` makes `gfx_icon_art.c`; `preview` makes the three icon sheets used by the guide.

**As many applications as the device holds** (the owner, 2026-11-16): at most 24 installed, each with a guaranteed 2 KB store. A module is at most 48 KB and occupies whole sectors of `appcode`. Files are counted in 4 KB blocks. A read-only package may bring 64 KB; `"writes_files": true` reserves 32 KB for its files, including packaged data. The build and Perinkpheral OS require that privilege for `file_write`. An installation checks the new store, code, files, existing writer reservations and 13 spare filesystem blocks before downloading and again after reading the manifest (`app_room.c`, `web_apps.c`). `/api/status` reports storage use.

**Put off: BLE** (the owner, 2026-11-13). The C6 has BLE 5, no classic Bluetooth. A Perinkpheral OS service for media keys would own pairing and bonds; applications would request its roles. Measure flash and heap cost beside TLS before adding it. No BLE service is implemented.

**How soon a redraw is shown** follows from where it was asked: from `app_on_button` at once, from `app_on_timer` and `app_on_data` by the e-paper policy. Flags on `screen_redraw`: `HOST_REDRAW_SOON` - show it now although nobody pressed anything; `HOST_REDRAW_CLEAN` - a full refresh, for a new picture; `HOST_REDRAW_NO_BLINK` - now, and not as the full refresh Perinkpheral OS makes after every few partial ones: for pictures in a row; `HOST_REDRAW_QUESTION` - the picture asks what OK answers: OK reaches the application only when it went down after that picture was on the panel, as Perinkpheral OS's own questions take theirs (`scene_t.question`, `is_press_for` in `host.c`). With NO_BLINK, ghosting accumulates until a full refresh. Applications have no redraw quota. Frequent refreshes consume energy and increase panel wear. A row of pictures is shown as fast as the panel takes them; any other request has a floor of one refresh a second.

What a handler may count on: one handler runs at a time and has 3 seconds; it returns nothing and leaves requests (`screen_redraw`, `screen_leave`, `screen_request`) that take effect when it returns; presses are not lost unless sixteen wait already, timers of one id collapse into one, and the pieces of one answer arrive in order - a setting saved or an alarm may come between two of them.

There are no pointer callbacks. An application exports functions with fixed names (Perinkpheral OS skips the missing ones):
```

                                    // and _PRESSED, _LONG_PRESSED as what it meant: BTN_OK_PRESSED
```

- **An application draws only inside `app_on_draw()`.** Handlers change the state and call `screen_redraw()`; Perinkpheral OS calls `app_on_draw()` when it needs the frame, with a white surface, and the drawing calls answer with an error anywhere else (measuring text works anywhere). Perinkpheral OS puts the frame together, compares it with what the panel shows and decides whether and how the panel is refreshed - so there is no `gfx_flush`, no partial-or-full choice in the application's hands, and an application cannot leave a half-drawn screen.
- **Mistakes the build refuses** (`tools/perinkpheral build`, 2026-11-14): a function named like a handler that is none (`app_on_buton`), a call whose answer has nowhere to arrive (`timer_set` without `app_on_timer`, `alarm_set*` without `app_on_alarm`, `http_send` without `app_on_data`), a poll or intents of the manifest without their handler, drawing without `app_on_draw`, a string or a picture the code never names. A module that fails a check is removed.
- **Two further runtime diagnostics are logged** of a running application: a handler that took over 400 ms (`slow handler: on_draw took 520 ms`, once an instance) and more than 12 writes of the store in a minute (every one is a write of the flash).
- **The runtime also logs two errors**, once each: a drawing call outside `app_on_draw()` ("draws nothing: change the state and call screen_redraw()"), and a redraw that waits for the refresh policy ("a redraw waits 37 s") - a picture that does not come is otherwise taken for a hang.
- **The module is not trusted.** One that imports anything outside Perinkpheral OS API is refused before it runs. Every pointer and length it passes is checked against its 64 KB before Perinkpheral OS touches it, and coordinates and sizes beyond a few thousand pixels are refused, so that no call can cost more than the surface is large. A handler has 3 seconds: one that is still running then - a loop without an end - is stopped, and recursion is stopped before it runs through Perinkpheral OS's stack. A handler that traps or is stopped ends the application, and the screen says so.
- **Data arrives as values or in pieces.** `firmware/main/poller.c` fetches every poll of every installed application when it is due, one request at a time, over HTTP and HTTPS. A poll with `"pick"` in the manifest is read to the end by Perinkpheral OS, the connection is closed, and the application gets the values in one `app_on_picked()` call, reading them with `answer_value()` (`sdk/lib/app_values.h` turns them into numbers and text). Any other answer goes to the application as it comes: Perinkpheral OS reads up to 1 KB, copies it into the buffer the application named with `app_data_buffer()` and calls `app_on_data()` - flags say first and last, the HTTP status comes with the first piece, and a request that failed is one call with `HOST_DATA_FAILED` and no data, the status saying why: no network, no answer, a setting not set, a host not allowed, a timeout - an answer of values not read in a minute, of pieces in five, is one too -, a certificate the device does not trust, an answer over 256 KB (4 MB for one handed on in pieces: a calendar of some years is a megabyte or two), no memory. Either way an application that is not on the screen is loaded for the delivery and unloaded after it (`app_delivery.c`); a poll that cannot start at all - no network, no memory - is told only to an application on the screen. Seen on the device: `weather` asking Open-Meteo over HTTPS, on the screen and off it; a request takes about 6 seconds, most of it the TLS handshake, and the free heap goes down to about 80 KB while it lasts.
- **State lives in the store.** An application is unloaded whenever it leaves the screen, so what must survive goes through `kv_get` / `kv_set`: up to 1 KB per key and 2 KB for all the values of one application, its settings among them - counted as they lie in the storage, 64 bytes for a value and its length rounded up to 32, or many one-byte keys would fill the partition all applications share - keys of up to 15 characters, in the `appkv` partition. The namespace is `a.<name>` and an application's name cannot hold a dot, so no application can reach Perinkpheral OS's settings or another application's values. `hello` reads its count when it starts and saves it in `app_on_terminate()`.
- **Text is bytes, and what is not ASCII Perinkpheral OS draws as well as it can.** Perinkpheral OS hands on the UTF-8 of an answer as it came - a value picked from JSON is cut between characters, never inside one - and an application may store it and send it back. The fonts have ASCII only, and `gfx_fit_text` cuts between characters. What is beyond ASCII is drawn by Perinkpheral OS, the same in every application, down a ladder: the letter's own glyph from a **glyph pack** when one is there (`gfx_pack_add`; `tools/perinkpheral glyph-packs` makes `latin`, `cyrillic` and `greek` - 32, 18.7 and 1.4 KB, 14 of the partition's 16 sectors: Departure Mono's letters as it has them; Jersey's Latin as it has it, 191 of the 232; Jersey's Cyrillic - every letter of the pack: Russian, Ukrainian, Belarusian, Serbian, Macedonian, Bulgarian, Kazakh - made by `tools/cli` (`JerseyCyrillic.kt`) from the Latin glyphs of the same face, mirrored, cut and joined, with stems and bars of the face's weight, so one description serves every face. Jersey 20, the face of the largest size alone, is left out for room, and Jersey has no Greek: there the ladder goes on to the spelling); else its spelling in ASCII by a table (`spelling.h`, made by `tools/perinkpheral spelling`: "Moskva", "Strasse", "Athina", a typist's dashes and quotes); else `?`. The degree sign (`\xC2\xB0`) is drawn in any font as a small square with a hole at the top of the capitals. On the device the packs live in a partition of their own (`glyphs`, 64 KB, mapped: `firmware/main/glyphs.c`), each in whole sectors, several side by side; a pack is written with its first bytes last, so one cut short by a loss of power is no pack. The user adds and removes them on the page (Settings, Language: the browser fetches a pack from the official catalog's `glyphs` folder and hands it to the device - `GET` / `POST /api/glyphs`, `POST /api/glyphs/remove?name=`), and the picture on the panel changes at once. Seen on the device: Russian, German and Greek in the calendar with the packs, spelled without. The Kazakh schwa, which the font lacks, is its Latin one's shape.
- **A complete answer has LAST.** Only `HOST_DATA_LAST` makes a streamed answer whole. `HOST_DATA_FAILED` may follow earlier pieces and invalidates all of them. Boundaries are unspecified, even inside a character or a marker. An interruption may end with neither LAST nor FAILED. **An answer may simply stop.** An application that was loaded off the screen to take an answer in pieces gives way the moment the user presses a button; the pieces still to come are dropped, it is told nothing, and the poll is fetched again in a minute, or sooner when its pace is shorter. An application keeps what it shows until an answer has come whole.
- **No floating point.** The interpreter is built without it - the chip has no FPU, and soft float in Perinkpheral OS was 34 KB - and without reference types, extended constants and compact imports; a module still has its one table of functions and calls through pointers. the build (`tools/perinkpheral build`) refuses an application whose code has a float operation and says which; one that got onto the device anyway stops when it reaches it. Numbers are integers - tenths, hundredths - and `sdk/lib/app_values.h` reads them that way.
- **No C library.** Applications are linked with `-nostdlib` against `sdk/lib`, a few hundred bytes of string building and the `memcpy` family, and `app_alloc.h` - an arena over what the page has left after the stack and the static data (`app_alloc`, and `app_alloc_mark` / `app_alloc_release` to give back to a mark; the build says how much is left); `printf` alone would take a quarter of the 64 KB. `hello` is 878 bytes.
- Time: SNTP on every Wi-Fi connection, the time zone is a Perinkpheral OS setting.

### E-paper policy
Implemented in `firmware/components/epd/refresh_policy.c` (pure, host-tested). **The policy's numbers are user settings**: fields of Perinkpheral OS's settings with a range each, stored in NVS and followed by the display service: Display in Settings on the device, and Display on the page. The defaults start from Waveshare's recommendations for the 4.2" V2:
- data-driven updates (`app_on_data`, a timer, the clock) - no more often than once per **60 s**, counted from the start of the last such refresh, so that a clock can show minutes: what the user did in between - opened the application, pressed a button - does not put the next one off, and one that comes a second early is in time. Waveshare's own advice is 180 s and the panel is rated for a million refreshes; a user who wants the panel to last longer raises the number;
- reaction to a button - the user is looking at the device - **at once**, no pause by default; visible latency also includes the handler, event queue and panel refresh (measured at about half a second for a partial refresh);
- full refresh - **never** by default but when the application on the scene changes, as an e-reader does it (the owner, 2026-11-17); a number of partial ones before one is a setting;
- at least one update per **24 hours** (a deadline of Perinkpheral OS's).

Fixed policy and rendering rules:
- Full refresh when the application on the scene changes; the first update after start is always full.
- The panel goes to deep sleep (mode 1, RAM is kept) after every full refresh and 1.5 s after the last partial one, otherwise it degrades irreversibly. Its voltages are off after every refresh either way: the controller does that itself. The chip does not go into light sleep while the panel is awake, and the panel's lines keep their levels when it does (`gpio_sleep_sel_dis`).
- **Fast refresh** is a setting (`refresh_fast`, on by default since 2026-11-17, on the page): Waveshare's `Init_Fast`, its 1.5 s waveform. A full refresh measured 2.2 s with it and 2.7 s without. Not for the cold.
- No animations and no real-time progress bars in Perinkpheral OS's own screens. An application that wants a row of pictures has `HOST_REDRAW_NO_BLINK`; the panel itself takes half a second for a partial refresh of the whole frame (0.41 s of it BUSY), and the application its time to draw, so that is three pictures in two seconds at best. `badapple` in the catalog is the test: 200x150 unpacked and drawn in about 0.1 s a frame by the interpreter.
- 1 bit per pixel. Fonts are bitmap, pre-converted (`tools/perinkpheral font`), ASCII and the glyph packs; the readable minimum is ~10 px.

### Web UI (on the device, `esp_http_server`)
What exists:
- `GET /` - one gzip-compressed page assembled by `tools/perinkpheral page` from `firmware/main/web/`. **Installed apps** lists applications with settings, information, Remove and compatible Update; **Update all** appears for at least two compatible updates. **Catalog** includes installed applications, marked Installed or Update, and uninstalled ones with Install; Refresh fetches the sources again. The city or custom zone and the time server share one Save, which writes `/api/settings` and, for manual time, `/api/clock`. **Credits** lists the project, dependencies and fonts. The page uses the device's language. Its links include `#settings:time`, `#apps:weather` and `#apps:catalogs`.
- `GET` / `POST /api/settings` - Perinkpheral OS's own settings but the network: the name, the time server, the time zone, and how the panel is treated - seconds between refreshes nobody asked for, hours before a refresh is forced, the full refresh after so many quick ones (0: always full, 255: never, the way e-readers offer it), and whether greys are dithered. What can take effect at once does.
- `POST /api/restart`.
- `GET /api/status` - name, firmware, slot, whether the image is on probation, Wi-Fi phase, network, address, free memory, and why the device last started (`reset_reason`: 3 a restart asked for, 4 a fault, 5 the interrupt watchdog). After a fault `last_panic` is its record, kept in RTC memory through the restart (`firmware/main/crash_note.c`): how many starts ago, the reason, the task, the program counter and the code addresses found on the stack - `riscv32-esp-elf-addr2line -pfiaC -e build/perinkpheral.elf <addresses>` names the place.
- `GET /api/log` - the last 4 KB of the device's log, as text: what the console would have shown, kept in memory for when there is no cable. `X-Log-End` is where it ends, for `?since=`; `X-Log-Boot` is the run of the device it is of, another after every restart.
- `POST /api/wifi` `{"ssid", "password"}` - validated like every setting, stored, and the device restarts to join.
- `GET /api/apps` - the installed applications, each with its settings as the manifest declares them and their values (a secret only as set or not); `POST /api/apps/settings?app=<name>` `{"key": "value"}` - checked against the manifest, stored in the application's store, the application told (`app_on_settings()`) and its polls fetched again at once; `POST /api/apps/remove?app=<name>` - its files; the list of applications is read anew, with no restart; `GET /api/apps/removed` - the names of removed applications whose settings are kept: the page offers those first when adding one, marked "settings kept". The gear on an installed tile opens its visible settings; hidden keys remain writable through the API.
- `POST /api/clock` `{"unix"}` - the clock set by hand, as Settings on the device sets it, from 2026 to 2100, and only while the network's time is off.
- `POST /api/time` `{"tz"}` - the time zone, a POSIX TZ string; it takes effect at once, with no restart. The page works the string out from the browser's own zone and offers it; a device that was never told its zone gets it along with the Wi-Fi network, so setting the device up is one step.
- `POST /api/reset` - factory reset: the settings and the applications' stores are erased on the way up, and the device comes back with its setup access point. The page has a button for it.
- `/api/dev/...` - the development tools, only in a build with `APP_DEV_CONSOLE`: `GET screen` (a 1-bit BMP of what the panel shows), `POST button`, `POST open`, `POST app` (upload a file of an application), `POST run` (restart into an application), `POST flash` (409: use the recovery update protocol), `POST kv` (a value into an application's store), `POST restart`, `GET sockets` (every socket of the device and who is on the other end), `POST crash?kind=wdt|abort` (a deliberate fault, to test the record and the way back).
- The browser downloads releases from the existing GitHub Pages mirror before entering recovery. `/api/ota/release` returns 409: recovery has no HTTPS downloader. The flasher at https://perinkpheral.dev/flash reads `flash/index.json` from the firmware repository Pages. `tools/perinkpheral flash-manifest` generates first-install and data-preserving migration manifests.
- `POST /api/reset` and `/api/wifi` wait for Confirm on the device's own screen, a minute at most (see Open). They and `POST /api/apps/install` wait on a task of their own (`WEB_WAITS` in the table of routes): the web server has one task, and the page would hear nothing while one of them waits. One such request at a time; another meanwhile is "Device busy.".
- `POST /api/ota/recovery` selects recovery and restarts main. The page's **Device > Enter recovery** uses `?manual=true`, which skips the planned-update hint; without it, main records that an upload is expected. Recovery accepts a binary at `POST /api/ota`, checks its header before asking for physical OK, then writes only `ota_0`. Main refuses direct uploads with 409. `/api/status` distinguishes `mode: application` from `mode: recovery`, and reports `ota_protocol: 1`. Clients wait for the intended image identifier and completed probation, not merely a restarted HTTP server.

**Firmware over the network.** The upload is refused before a byte is written unless it is an image of this project (the image and description magic numbers and the project name) built for the partition table the device has. The new image starts on probation: it is confirmed only once the way the next update would arrive is open again - the web server is up and the device is on its network, or, with no network stored, its setup access point is up and it has run for 20 seconds. An image that has not got there within 3 minutes marks itself invalid, and the device restarts into recovery. There is no automatic return to the previous full firmware. The receiving (`ota_stream.c`) and the verdict (`ota_health.c`) are pure and host-tested; `recovery/main/ota.c` alone writes the main slot; `firmware/main/ota.c` selects recovery and confirms or rejects probation.
**Recovery contract (protocol 1).** Recovery is a separate ESP-IDF project in `recovery/`, built with every main firmware. Both use `firmware/partitions.csv`. Ordinary OTA never writes recovery, the bootloader or the partition table. Recovery reads `cfg/name`, `cfg/wssid`, `cfg/wpass` and `cfg/language` without repairing or erasing NVS. It always starts the open `perink-recovery` access point at `192.168.4.1`, and also tries the saved network when its credentials are usable. Its routes are only `/`, `GET /api/status` and `POST /api/ota`; main's settings, log and development routes do not run there. It does not load applications. The existing panel driver and antenna configuration are shared. The factory image must be selected durably, clearing both OTA journal copies, before main erasure begins; otherwise a stale VALID record may select the same failed sole OTA image again.

BACK held for three seconds at reset enters recovery through the standard bootloader. Only OTA metadata is cleared, never NVS or applications. A fresh USB install also starts recovery; BACK, labelled "Exit recovery", explicitly validates and tries the installed main with probation; a missing or damaged image cannot be started and needs another upload. Recovery never automatically retries a failed main. The 2026-11-18 hardware checks cover USB migration with byte-identical data partitions and successful OTA on the battery with USB absent. The owner cannot disconnect this device's battery, so controlled power-loss qualification remains pending on a suitable fixture; compiling, host tests and removing USB do not establish that behavior. Results and remaining cases are in `docs/testing/stability.md`.

Recovery uses Perinkpheral OS's `notice` and `kit` drawing, icons and English/Russian word tables. It reads the saved language and maps installed glyph packs read-only; absent or damaged packs fall back to ASCII spelling. NVS initialization itself uses a read-only partition descriptor, so IDF cannot repair the store during recovery startup. Confirmation shows the complete version, and network instructions are confined to the waiting/error screen. Updating, checking and restarting use the same working notice as main.

An intentional update carries a one-use UI hint: after selecting factory, main writes an eight-byte magic/complement pair at offset 64 of `otadata`, outside IDF's two boot records. Recovery consumes it before networking and accepts it only after a software reset. It does not affect boot selection, image validation or physical consent. Missing, unreadable or unconsumable hints mean recovery, never an assumed update. The requested-update path keeps one "Preparing update" screen while Wi-Fi connects and the header arrives, then asks for confirmation. Only a stalled handoff (30 seconds) exposes network instructions. Manual entry, failed probation and restarts after interrupted writes show recovery immediately; with saved credentials they show "Connecting to Wi-Fi" until connected or the same deadline, then the appropriate page address or access-point instructions. First installation with no saved network exposes the access point immediately. Older main images without the hint use this recovery path.

The one-time migration requires USB and stable power because the partition table and bootloader change. All data partition addresses and sizes are retained. Use the migration manifest (no whole-flash erase or apps image); normal `flash` includes bundled apps and replaces their partition. `app-flash` writes main at its explicit address and clears OTA metadata, leaving recovery and user data intact; start main with BACK. A normal first-install manifest carries both images. Recovery fixes require a deliberate USB maintenance operation: `recovery-flash` writes only factory and preserves main, OTA metadata and user data. The web flasher's Keep data mode can update both main and recovery on the existing layout as well as migrate the old one. Keep its protocol, layout descriptor and network keys compatible with future main releases.


### Catalogs
Applications are installed the way a Debian system installs packages: the device knows a few **sources**, each the address of a folder of static files, with an index in it; the index lists available packages, and the browser reads it. The device downloads prebuilt packages over HTTPS; it does not run Git or build applications. A source that is not `https://` is refused. Developers can use `tools/perinkpheral publish <folder> --repo owner/repository` to build and publish `catalog/` to their own public GitHub repository. The command uses Git and an authenticated GitHub CLI on the computer, preserves files outside `catalog/`, and prints the repository URL to add under Catalog > Sources. `catalog <folder> --out <dir>` remains available for other HTTPS hosting.
- `tools/perinkpheral catalog <folder> --out <catalog>` builds every application of a folder and writes `catalog.json` beside them: for each its name, title, version, `abi`, and its files with their sizes and SHA-256.
- The official catalog is https://github.com/Perinkpheral/perinkpheral-apps: seventeen applications - `air`, `badapple`, `calendar`, `clock`, `ha`, `iss`, `kit`, `life`, `metals`, `pomodoro`, `rates`, `status`, `stocks`, `stopwatch`, `sun`, `timer`, `weather`. Its `catalog/` is the fixed first source. The firmware bundles `hello`, the SDK sample, separately. A removed sample can be installed again with `tools/perinkpheral run sdk/apps/hello` in a development build or by flashing the bundled apps partition.
- **As many as fit.** A device holds up to 24 applications, as much as their room allows (see Perinkpheral OS API); a catalog index may be at most 512 KB. The page installs and removes in a click, and **an application that is removed keeps what it stored** - its settings among it - for when it comes back (`&forget=1` on the removal erases that too), until the stores' partition is full: then what removed applications left is the first to go.
- The page passes the index on from the source as it comes (`GET /api/catalog?source=<n>`): the device does not read it. Installing (`POST /api/apps/install`) downloads the files the index lists, takes each only if its size and SHA-256 are what the index says, reads the manifest with the parser that runs applications - one made for another `abi` is refused with those words. `app_store_commit_all` writes a commit marker before replacing files and removes it after the last replacement. A marked package stays unavailable until recovery finishes. Recovery and scene reload run together in the main event loop, so an incomplete package cannot run with mismatched files. Nothing restarts: Perinkpheral OS reads the list of applications anew (`host_reload_apps` - the scenes are made again, the poller's schedule too, and an application that was on the screen and is gone gives it to the menu). `GET` / `POST /api/sources` are the list.
- There are no signatures: what vouches for an application is HTTPS to the source the user chose. The application is in the sandbox all the same.

### Power and profiles
The battery is connected. There is no detector of the power source in version 1, so the profile is a Perinkpheral OS setting, `power_saving`: 0 never (`plugged`, the default), 1 always (`battery`), 2 auto. It is in Settings on the device (General, Power saving: Disabled, Always, Auto) and on the page. **Auto** saves whenever no computer is on the USB cable, which is the one thing the board can tell (`usb_serial_jtag_is_connected`: USB host's packets, looked for every 5 s): plugged into a computer the device is as when plugged, otherwise as on its battery - and a charger looks like the battery.
- **plugged** - Wi-Fi always on, the web UI available, any `every`, polls on schedule.
- **battery** - **light sleep** between polls: memory, application state and the framebuffer are kept; wake-up by timer and by any of the four buttons (`gpio_wakeup_enable`). Wi-Fi comes up for the poll and goes down; the web UI is available for 2 minutes after a button press, after power-up and after the profile is changed. The minimum `every` is 300 s, anything smaller is rounded up. The board's current in light sleep has not been measured - measure it before any promises about battery life.
  - How it is built (`firmware/main/power.c`): the chip sleeps by itself whenever no task runs (ESP-IDF power management with tickless idle; `light_sleep_enable` follows the setting at run time). The radio is counted: the poller holds it while something waits for the network and gives it back after, a press holds it for two minutes, and with nobody holding it `wifi_set_radio(false)` stops Wi-Fi without the plan taking that for a lost network. A network that does not answer in 20 s is given up until the next poll's least distance. The buttons task waits for a level instead of sampling every 5 ms, or the chip would never sleep. The header's icon says how the last attempt went.
  - With a computer on the other end of the USB cable the chip does not sleep (`CONFIG_USJ_NO_AUTO_LS_ON_CONNECTION`), so the console and flashing work on the bench - and so sleep itself has only been seen to be allowed, not seen: the radio's schedule was watched from the network, the current was not measured.
- **Deep sleep is deferred to version 2** (the owner, 2026-11-12). A cold start on every wake and no wake from button 4 require a separate design. Version 1 uses light sleep.

### TRMNL compatibility - as an application, not as a platform
The owner chose TRMNL compatibility as an application, with no changes to Perinkpheral OS. No `trmnl` application is implemented.

## Implemented architecture decisions

The owner's architecture decisions of 2026-11-12. The mechanisms below are implemented.

**Who may change what.**
- the main event loop owns Perinkpheral OS's state: the settings, the list of installed applications, the scenes. Every other task - the web server, the poller, Wi-Fi - reads a **published snapshot** of the settings and of the list, and changes nothing of them.
- A snapshot carries a version: a reader notes it, copies, and copies again if it changed meanwhile, with a compiler fence on each side of the copy; no lock on reading them. A reader may see what was true a moment ago.
- What a service keeps of its own is its own, under its own mutex: Wi-Fi's state, the status, the power profile, the display service, the poller's schedule and queue, the deadlines. the main event loop asks them like anybody else. The owner retained this division on 2026-11-15: the main event loop owns screens and applications; services own their state.
- A change is a **command through the event queue**: the handler posts it and waits for the main event loop's answer, as the development tools do. A page waits up to the length of a refresh; that is fine.
- Posting into the queue may be refused when it is full, and says so: the caller decides (a command answers "Device busy.", a deadline stays due, a press is lost).
- **Perinkpheral OS's settings are a store by key, and Settings is only one of its writers** (the owner, 2026-11-17: "settings must not know their consumers; another settings application must give the same behaviour"). Every setting is a line of one table (`appconf_fields()` in `firmware/components/appconf`, pure): its key - the one name it goes by on the page and in the system API, NVS keeping it under a short name of its own - its type, its range, whether it is a secret, whether it is taken at start, whether it is set its own way (the network, asked about on the device). `settings.c` is the store and nothing else: it reads and writes NVS by the table, checks a change whole, publishes the snapshot and tells whoever follows it (`settings_watch`), knowing none of them. Whoever puts a setting into effect follows the store itself: the clock and the panel (wired in `main.c`, for components that know no settings), the look - the typeface, the language, the greys - in the main event loop, the application runtime, power, the poller, the header. The page (`/api/settings`) and an application with system access (`sys_setting_*`) use the same validation rules; the application API exposes only its explicit allowlist of page-visible keys, never an internal setting such as `refresh_min_button_ms`; Settings is such an application and could be replaced by another.
- An application is installed in two steps: the files are fetched into a staging place from the web server's task, and put in place by the main event loop together with reading the list anew.

**How an application is addressed.**
- Inside Perinkpheral OS an application is its **id: 31 bits of the SHA-256 of its module and manifest, never 0**. A new version is another application to everything that was waiting for the old one; the same package installed again is the same, regardless of version-string ordering. System applications are known by their names. The name stays for people and for the disk: the folder, the catalog, the page, the store, the application to return to after a restart.
- The schedule of polls, the requests and the alarms are kept **by id**. Removing an application removes its own; nothing else touches them.
- Several alarms an application: `alarm_set(id, seconds)`, `alarm_set_at(id, unix_time)`, `app_on_alarm(id)`.
- **Intents by subscription**: an application names in its manifest (`"intents"`) the kinds of news it wants, and gets them through `app_on_intent(type)`, loaded for it if it is not. Three kinds: the time changed (`time_changed`), the network is there again (`network_up`), and the device was powered up or restarted (`started`). **`started` is how an application runs without being opened**: a restart forgets alarms and requests under way (a poll's own pace is kept), and an application that asked is loaded off the screen after it and sets them going again from its store - a calendar puts its alarm back, a messenger makes its first request. Polls need none of this: they come from the manifest.  A kind Perinkpheral OS does not know fails the build (`tools/perinkpheral build`).
- `app_on_terminate()` is called before an instance is unloaded, whatever the reason - it left the screen, a delivery in the background is done, the device restarts, the application is removed - unless a fault stopped it, which ends it at once; light sleep keeps it loaded. `app_on_blur()` keeps its narrow meaning and comes first. State is saved in `app_on_terminate`.

**Time.** `firmware/components/deadlines` owns Perinkpheral OS deadlines. OTA probation and button debounce keep their own timing.
- **One module owns every deadline** of Perinkpheral OS and does nothing else: the polls, the alarms, the timers of the application on the screen, the panel's daily refresh, the while after a press, Wi-Fi's retries. Set a deadline, take it back, ask for the nearest; one that has come is an event in the queue.
- **The scale is absolute time.** The RTC always has one - the user's, the network's or 1970 - and runs through sleep. Behind the API everything is a moment: "in 20 minutes" is turned into one when it is set.
- When the clock is changed - by the network or by hand - deadlines that were set as "in so long" move with it, and those set as "at such a time" stay.

**Stopping.**
- A restart and a factory reset are one sequence in the main event loop: `app_on_terminate` for the loaded application, the panel's refresh to its end, the poller held, and only then the restart. Light sleep is no stop: ESP-IDF's power management, with everything loaded as it was. No waiting on the off chance: every step is known to be done.

**Memory.**
- `firmware/components/wasm3/m3_area.c` takes a 128 KB application area at start, reset whole on unload: 64 KB for wasm memory and 64 KB for interpreter allocations. The owner enlarged the latter on 2026-11-13 for Calendar. Applications use `-Oz` and link-time optimization; the interpreter uses 512-byte code pages. The build reports an estimate of interpreter use and warns if it exceeds the area. Exercise application paths on the device to check actual headroom.
- `firmware/main/app_code.c` maps the 320 KB code partition read-only. Modules occupy contiguous whole sectors after a 32-byte record written last. If free sectors are fragmented, compaction first saves each moved module to its application folder; a restart imports that file again. the main event loop imports staged modules with no application loaded. Manifests, package files and stores stay in their own storage.
- An image carries the layout id made from `partitions.csv` (`image_layout.c`). OTA refuses an absent or different layout id before writing. A partition-table change requires a USB flash.
- TLS admission checks both total free heap and the largest contiguous block.

**The contract.**
- `http_send(tag, ...)`: the application chooses the tag, a number it has a name for, and the answer comes with it. Tags are an application's own; two applications with the same one never meet.
- An application asks for data; "there is no network" is one of the answers, and a request that failed says why: no network, no answer, a host the manifest does not allow.
- The header's icon says whether the last use of the network worked.
- The system API gives applications by id, not by their place in a list.
- `"system": true` stays one consent for all of it.
- `firmware/main/poller.c` connects four parts: which polls are wanted and at what pace (`poll_schedule.c`, pure - when each is due is a deadline, the alarms are deadlines outright), the one that talks to the network (`poller_net.c`), the requests applications make, waiting their turn (`firmware/components/appstore/request_queue.c`, pure), and what ties them to Perinkpheral OS (`poller.c`: the task, the radio). The task sleeps until it is woken and has no clock of its own. Calling the main event loop and waiting for it is `events_call_patiently()`.

Application memory is fixed rather than declared in each manifest. Perinkpheral OS keeps one instance and resets its arena on unload; moving allocations and compacting a runtime heap are outside this design.

## Milestones

5. **Web UI and catalog.** Installation, removal and updates, settings, log, control, firmware uploads and release downloads are implemented.

The developer guide is built from `docs/guide/source/guide.html`; Russian comes from `docs/guide/source/guide.ru.txt`. The English source governs. An API addition is documented there; a changed signature or meaning needs a new ABI.

## Continuous integration
The owner's rule (2026-11-17): every push of every repository is built and tested; a push to `main` is also a release, with the version raised by itself; a push to another branch builds the same and releases nothing. The version of a release is the greater of the one the repository writes down (`VERSION`, `pluginVersion`, the integration's manifest; none for the catalog and the portal) and the last release's with its patch one up; a build of another branch is `<version>-<commit>`. Runs of `main` go one at a time, so each takes the version the one before released. The notes of a release are the commits since the one before - for the firmware, the version's section of `CHANGES.md` when there is one.
- **This repository** (`.github/workflows/ci.yml`): the host tests with the layers and the languages; Kotlin tests of the shared firmware-update client and Node.js tests of the firmware-update and manual-recovery pages; the applications of `firmware/test/sim` in the simulator, each frame held against a PNG that was looked at and kept (`tools/perinkpheral sim-test`; a frame that differs is the run's artifact, `--update` writes the pictures anew); the firmware built twice in ESP-IDF's container - for release, and with the development tools for debugging (`<version>-debug`) - each with its separate recovery image and the files of a first flash; the size of the image and of the RAM against the last build of `main`, in the run's summary and on a pull request. The printable-enclosure job checks the STEP source, 3MF geometry and archive with Python 3.12 and the CAD dependencies in `tools/case/requirements.txt`. A release carries both firmware builds and enclosure print files; then `flasher.yml` puts every release's firmware files on this repository's Pages for the flasher.
- **Generated files and guides** runs on Ubuntu 24.04, Java 21 and a C compiler. Chromium prints both PDFs; poppler-utils extracts their text; fonts-dejavu-core, fonts-liberation and fonts-noto-core supply fallbacks, with Departure Mono in `assets/fonts`. CI requires a complete Russian translation and matching guide limits, compares committed generated fonts, icons, marks and guide screen pixels, and checks the OpenAPI paths and methods against the firmware route tables. Both PDFs and glyph packs are release assets; glyph sheets are run artifacts.

## Conventions
- Everything is written strictly in English, with a plain hyphen `-`, never an en or em dash.
- **Interface text is short and standard**: on the panel, on the web page, in the answers of the API. The words every interface uses - Save, Update, Remove, Install, Factory reset, "Invalid value.", "Storage error." - and not a sentence of our own making ("Read them again", "refreshes nobody asked for"). No paragraphs of help under a field: a label that needs explaining is the wrong label. Simple, exact, competent.
- Nothing in the repository depends on one developer's machine: no home-directory paths, no fixed serial port names, no OS-specific steps in code, tools or documentation.
- **Single-source definitions checked by the build** (2026-11-14): a call's signature - in `sdk/host_api.h`, and Perinkpheral OS's table of imports is made from it (`tools/perinkpheral imports`, by the core's one reader of the contract); a task's priority and stack - in `firmware/components/board/include/priorities.h`; what is checked before a web handler runs - the request's origin, the memory - in the table of routes (`web_route_t`), and no handler repeats it; what is promised of the flash - the largest module, an install in hand beside the file system's spare, every store full - against `partitions.csv` in `firmware/main/flash_budget.c`, which does not compile when a number on either side breaks a promise; the guide's table of limits - against the headers, by `tools/perinkpheral check-limits` on every build of the guide. **The layers** (2026-11-17) - by `tools/perinkpheral check-layers` with the host tests: which component may know which, that none knows Perinkpheral OS's own code, that the pure modules know nothing of ESP-IDF, that the views and the scenes know no service, that the settings' store knows none of the settings' consumers, that the services know no screen, and that what the web server's handlers change of the main event loop's state they change through the main event loop. A new component, a new pure module or a new service is given its place in its tables when it is written. Time constants stay beside the code that uses them: most are a module's own pauses.
- JSON documents - manifests, the page's requests and answers - are read and written by `firmware/components/appstore/json_tree.c`, the project's own: a tree, integers only, no floating point (cJSON and what it pulled of the C library were 9.7 KB of the image). Answers that arrive in pieces are `sdk/lib/json_pick.c`.
- SPDX header in every source file, C11. Logic that does not need hardware is pure and host-tested; main's `settings.c` owns Perinkpheral OS's settings; recovery's `settings.c` only reads them through a read-only partition descriptor.
- When debugging hardware: the vendor's reference code and the datasheet first, hypotheses after. Do not suggest "check the wires".

## Branding
- **The logo is the word `perINKpheraL` set in the device's square font: lower case `per` and `phera`, capital `INK` and a capital `L` at the end, all of one height in the same squares, with no plate, frames or dots.** The mix of capitals and lower case inside one word is the mark itself. On the panel - black on white, scale 5 (27 px squares), 357 px.
- **The mark is two corners that frame an empty square**: the top right one and the bottom left one, a stroke each, set apart on the diagonal - the frame of a screen with nothing asking for attention in it. The owner found it on 2026-11-13 in Perinkpheral OS's own `update` icon (`gfx_icons.c`, eleven cells: each corner six cells across and six down, the two three cells apart; drawn six by six on 2026-11-17, at the owner's word) and named it the icon and the logo of the whole project. The word `perINKpheraL` stays the wordmark; the mark is what stands where a word does not fit - a favicon, an avatar, an icon of an application. It is made in `assets/mark` (SVG and PNG, bare and on paper) from the icon's own cells by `tools/perinkpheral mark`, which also gives the cells for the copies that stand in code (the portal's `Brand.tsx`, the device page's markup), and stands as the icon of the device's page in a browser, in the repository READMEs and as the icon of the Home Assistant integration. **It stays the `update` icon too** (the owner: "a superb decision that the icon is right there"): the question about a new firmware is asked under the project's own mark.
- The square font: every glyph is a square on a grid of 3 strokes × 2 gaps (5+6+5+6+5 = 27 px), no ascenders or descenders, diagonals allowed. Implementation: `firmware/components/gfx/font_square.c`.
- The splash at power-up is the About application's picture: under the mark the version of the build, a QR code of the project's address, and `(c) 2026 Max Grakov` and `MIT License` in the small font. When the application cannot be shown there is no splash: the device goes straight to where the splash would have led.
- **The square font is for the word `perINKpheraL` only.** All other text on the device (splash, menu, Perinkpheral OS applications) is set in **Departure Mono** (SIL OFL 1.1, https://github.com/rektdeckard/departure-mono), a monospaced pixel font. It is rasterized by `tools/perinkpheral font` once, at 11 px, where it lands on its own pixel grid; every size on the device is that bitmap with each dot drawn 1, 2, 3, 4, 6 or 10 pixels large, so a new size costs no flash. It was chosen on the panel against Jersey 20, Jersey 25 and Terminus. **Jersey** (SIL OFL 1.1, https://github.com/scfried/soft-type-jersey; heavier, proportional) is the second family the user can pick. The number in a Jersey face's name is the height of its capitals in pixels on its own grid, so Jersey 25 is the medium size and Jersey 15 the size of Perinkpheral OS's text; the files are `assets/fonts/Jersey{10,15,20,25}-Regular.ttf` with `OFL-Jersey.txt`. The file is `assets/fonts/DepartureMono-Regular.otf` with `OFL-DepartureMono.txt`. Outline fonts rasterized to 1 bit (Tektur was the first try) come out thin and ragged at this pixel density - use fonts drawn for the pixel grid. Fonts are OFL/CC0 only.
- Palette: black #141413 and paper #E9E7E1 (on the device - the panel's native grey-white). Every Perinkpheral OS screen is black on white. Perinkpheral OS UI uses no halftones, dithering or gradients; applications may use dithered greys through `gfx_set_color`.
- Do not propose: a plate or frame around `INK`, dithered letters, white on black, decorations on the splash, other typefaces.

## Do not
- Do not pull in Arduino, ESPHome, LVGL, GxEPD2, Home Assistant.
- Do not give applications sockets: the network is only `polls` - to the addresses the manifest writes - and `http_send` in Perinkpheral OS's queue, by the `hosts` list.
- Do not build a declarative JSON layout into the core (it can be one of the applications).
- Do not keep more than one wasm instance in memory or more than one TLS connection.
- Do not use pointer callbacks in the ABI - named exports only.
- Do not change an existing ABI 3 signature, meaning, privilege, layout or constant without a new `abi`; additions preserve existing entries and carry `HOST_SINCE_<name>` stamps.
- Do not design for PSRAM: there is none.
- Do not measure battery voltage or detect USB supply voltage - no dividers or ADC, decided. The existing USB-host connection check for Auto is not a measurement of the power source.
- Do not "optimize" the panel driver past Waveshare's own: its commands, its waveforms and its waits as they are, CS per byte, bounded BUSY waits. No waveforms of our own (`0x32`).
